## 1. 집계 대상의 정의 — 전부 우리 선택이다

| 축 | 값 | 성격 |
|---|---|---|
| 지역 | 시군구 5자리 (`Region.code` 를 `LAWD_CD` 로 그대로 사용) | 저장소가 이미 그 단위다 |
| 주택유형 | **아파트 단일** | **우리 선택.** 이 엔드포인트가 아파트 전용이고, 연립·단독·오피스텔은 별개 엔드포인트다. `Region` 에 유형 칸이 없어 섞으면 무엇의 중앙값인지 말할 수 없다 |
| 전용면적 | **85㎡ 이하** | **우리 선택.** 국민주택규모라는 준거가 있으나, **상한을 두기로 한 것 자체가 규범적 선택**이다. 「국민주택규모라서 자연스럽다」가 아니라 「우리가 85 이하로 좁혔다」가 맞는 서술이다 |
| 기간 | 계약년월 기준 **최근 3개월** (실행 월 포함) | **우리 선택.** 실행 월은 신고 지연 때문에 거의 비어 있다. 그래도 빼지 않는다 — 빼는 것 역시 등재되지 않은 선택이고, 비어 있다는 사실은 표본 수로 드러나는 편이 낫다 |
| 표본 최소 | 통계별 **10건** | **우리 선택.** 준거 없음 |

값은 전부 `contracts/model_constants.json` 에 `(d) normative` · `our_choice` 로 등재돼 있다.
코드는 `constants[...]` 로 **fail-closed 조회만** 한다 — 기본값을 두면 그 기본값이 곧
등재되지 않은 모델 상수가 된다.

**전세·월세·매매에 같은 조건을 적용한다.** 한쪽만 조건이 다르면 뒤의 비율이 시장이 아니라
조건 차이를 재게 된다.

## 2. 단위

응답의 `deposit` · `monthlyRent` · `dealAmount` 는 **만원 단위**이고 **콤마가 섞인 문자열**이다.

```
"33,000"  ->  33000 * 10,000  =  330,000,000 원
```

콤마를 지우고 만원을 곱하지 않으면 3.3만원짜리 전세가 되고, 그 숫자는 판정을 통째로
거짓말로 만든다. 값이 빈 칸이면 **0 이 아니라 제외**다 — 0 으로 읽으면 중앙값이 내려가고
그 방향은 관대한 쪽이다 (HANDOFF 불변조건 7).

**전세와 월세의 구분:** `monthlyRent == 0` 이면 전세다.

## 4. 파생 계산 둘

> **⚠️ 아래 4.1 · 4.2 는 2026-08-15 이전의 계산이다.** 산식(무엇을 무엇으로 나누는가)은
> 그대로지만 **무엇을 대입하는가가 바뀌었다** — 지역 전체의 중앙값이 아니라 **셀 단위
> 중앙값**을 대입하고, 지역 값은 그 비들의 중앙값이다. **정정은 4.3 에 있다.**
> 두 절을 지우지 않는 이유는 무엇이 왜 뒤집혔는지가 사라지면 다음 사람이 같은 결론을
> 다시 내리기 때문이다.

### 4.1 `conversionRatePct` — 전월세전환율

```
전월세전환율(%) = 월세 × 12 / (전세가격 − 월세보증금) × 100
```

**준거 — 원문확인.** 한국부동산원 「통계산출항목」 페이지의 산식을 그대로 옮겼다.
https://www.reb.or.kr/reb/cm/cntnts/cntntsView.do?mi=9807&cntntsId=1189

> 전월세전환율(%) = [월세 * 12 / (전세가격 - 월세보증금)] * 100
> 전월세전환율은 조사월까지 신고된 실거래 기반 산출

우리는 위 3절의 세 중앙값을 대입한다. 문서의 검산 예시(전세 1억 · 보증금 1천만원 ·
월세 90만원 → 12%)를 테스트가 그대로 확인한다.

- 분모(`전세가격 − 월세보증금`)가 0 이하이면 **비운다.** 그 자리에 아무 숫자도 넣지 않는다.
- 소수 둘째 자리에서 반올림한다 (표기 선택이며 모델 상수가 아니다).
- **자료는 국토교통부, 산식은 한국부동산원이다.** 계보의 `source_name` 이 그 둘을 같이 적는다.

### 4.2 `jeonseRatioPct` — 전세가율

```
전세가율(%) = median(전세 보증금) / median(매매 거래금액) × 100
```

**★ 이것은 「중앙값의 비」이지 「비의 중앙값」이 아니다.**

```
median(전세) / median(매매)      <- 중앙값의 비  (우리가 내는 값)
median(전세ᵢ / 매매ᵢ)            <- 비의 중앙값  (같은 물건을 짝지어야 성립)
```

둘은 다른 값이다. 실거래가는 **전월세와 매매의 거래 물건이 서로 달라 짝지을 수 없으므로**
비의 중앙값은 계산 자체가 불가능하다. 그래서 중앙값의 비를 쓰고, 그 사실을 계보의
`source_name` 에도 적는다.

- **한국부동산원 공표 전세가율과 다를 수 있다.** 모집단과 산출 방식이 다르기 때문이다.
  **우리 값을 그쪽 공표값인 척하지 않는다.**
- 매매 표본이 최소 건수(10)에 못 미치면 **갱신하지 않는다** — 이전 값을 유지하고 계보는
  출처 미특정(`unverified`)으로 남는다. 모자란 표본으로 계산해 내놓지 않는다.
- 다만 매매 표본 부족은 **외부 실패가 아니므로 배치 전체를 막지 않는다.** 막으면 전세가율
  하나가 나머지 넷을 인질로 잡는다. (매매 **수집 실패**는 외부 실패이므로 전건 규칙에 걸린다.)

> **연혁.** SPEC 3.1 은 원래 이 필드를 「가능(파생 계산)」이라 적었으나 전월세 엔드포인트에는
> 매매가가 없어 사실과 달랐다. 착수 시 이 점을 보고했고, 사용자가 매매 API 를 수집 대상에
> 넣기로 결정해 도출 가능해졌다. 그 전까지의 처리(갱신하지 않고 이전 값 유지)는 표본 부족
> 경로로 그대로 남아 있다.

### 4.3 ✅ 3차 정정 (2026-08-15, 사용자 승인) — **두 비율은 「비의 중앙값」이다**

SPEC 3.1 3차 정정 · 계약 결정 #35 의 집행이다. **4.1 · 4.2 를 함께 정정한다.**

#### 무엇이 뒤집혔나

4.2 가 「실거래가는 전월세와 매매의 거래 물건이 서로 달라 **짝지을 수 없으므로** 비의
중앙값은 계산 자체가 불가능하다」고 적었다. **거래 건을 1:1 로 짝지을 수 없는 것은 맞지만,
집계 단위를 셀로 두면 짝이 성립한다.** 4.1 의 「우리는 위 3절의 세 중앙값을 대입한다」도
같이 뒤집힌다 — 전환율도 셀 단위로 낸다.

```
셀 = 법정동(umdNm) + 단지명(aptNm) + 전용면적 구간

  1. 셀 안에서 각 통계의 중앙값을 먼저 구한다
  2. 셀 하나당 비 하나를 만든다   (산식은 4.1 · 4.2 그대로다)
  3. 셀들의 비에 중앙값을 취한다  <- 이것이 지역 값이다
```

- **거래를 데카르트 곱으로 짝지으면 거래가 많은 셀이 중앙값을 지배한다.** 전세 12건 ×
  매매 12건인 셀 하나가 144쌍을 내는 동안 1건짜리 셀 열 개는 열 쌍을 낸다 — 그러면 지역
  값이 그 한 단지의 값이 된다. 그래서 **셀 중앙값이 먼저**다.
- `aptNm` 만으로는 부족하다. 같은 시군구에 **같은 이름의 단지가 여럿** 있어 법정동을 앞에 붙인다.
- 면적 구간 폭은 **모델 상수** `ingest.market_pair_area_band_sqm` = 1.0 (정수 ㎡ 반올림) 이며
  **(d) 규범적 선택**이다. 공표 준거가 없다 — 1㎡ ↔ 5㎡ 에서 값의 최대 이동이
  0.12%p(전환율) · 0.46%p(전세가율)라 어느 값을 골라도 결과가 같지만,
  **고른다는 사실 자체가 우리 선택**이다.
- **표본 문턱은 새로 만들지 않았다.** 4.2 의 「매매 표본이 최소 건수에 못 미치면 갱신하지
  않는다」를 **짝이 성립한 셀 수**에 그대로 건다(`ingest.market_min_sample_count` = 10).
  짝이 성립한 셀은 셀마다 매매가 최소 한 건씩 있으므로 **셀 수 ≤ 매매 표본 수**이고,
  새 규칙이 옛 규칙을 포함한다.

#### 무엇이 그것을 뒤집었나 — 6차 실사가 원문확인한 **표본 설계**

한국부동산원 전국주택가격동향조사(국가통계 승인번호 304004)는 **단지(PSU) → 개별 호(SSU)**
로 층화 2단계 추출한 표본주택에 대해 **매매가격 · 전세가격 · 월세가격(보증금·월세)을 모두
산정**한다(설명자료 조사항목, 원문확인). 짝짓는 절차가 따로 있는 것이 아니라 **표본 설계
자체가 짝을 만든다.** 우리는 같은 호를 볼 수 없지만 **같은 법정동 · 같은 단지 · 같은 평형**
까지는 갈 수 있고, 셀은 그 구조를 실거래가 자료에서 흉내 내는 것이다.

실측(`diligence/FINDINGS-6.md` · 지역 10건 · API 60호출 · 원시 23,677건):

| | 중앙값의 비 (4.1·4.2) | 비의 중앙값 (이 절) |
|---|---|---|
| 전월세전환율 · 공표값 대비 평균절대오차 | **2.30%p** | **0.14%p** |
| 전세가율 · 공표값 대비 평균절대오차 | **7.65%p** | **2.44%p** |
| `risk` 가중치 밴드가 공표값과 일치 | **5/10** | **8/10** |

**전환율은 10/10 지역에서 옛 계산이 더 낮았다. 예외가 없다.** 낮은 전환율은 `tco` 의
반전세·저보증금 월세를 싸게 만드는 **관대한 방향**이다(불변조건 7).

#### 여전히 확정되지 않은 것 — 값을 지어내지 않는다

- **한국부동산원이 「비의 중앙값」을 쓰는지 「중앙값의 비」를 쓰는지는 원문에서 확정하지
  못했다.** 통계설명자료 · 이용자용 통계정보보고서(30쪽) · 조사개요 · 용어해설 · KOSIS 주석
  다섯 곳을 전부 열었고 **산식이 어디에도 없다**(접근실패 6건, FINDINGS-6.md E-1).
  **우리 값이 공표값과 가까워진 것은 정황이지 원문확인이 아니다.**
  4.2 의 「**우리 값을 그쪽 공표값인 척하지 않는다**」는 규율은 그대로 유지된다.
- **4.1 의 준거 URL 은 「오피스텔 가격동향조사」의 산출항목 페이지다** (본문이 다섯 번
  오피스텔이라고 말한다 · FINDINGS-6.md A4). 산식 문자열 자체는 우리 구현과 일치하지만
  우리는 아파트 실거래를 모으므로 **인용이 어긋나 있다.** 실사가 **아파트 쪽의 같은 성격
  페이지를 찾지 못했다.** 없는 URL 을 지어내지 않으므로 가리키는 것을 그대로 두고,
  그것이 무엇인지와 「아파트 대응 페이지 미확인」을 계보(`source_name`)에 적는다.
- 부동산원은 **주택재고량으로 가중**하고(정보보고서 9쪽) 우리는 **셀을 동등하게** 본다.
  가중을 넣으면 값이 어떻게 움직이는지 **재지 않았다** (FINDINGS-6.md E-11).

## 5. 도출하지 않는 셋 — 비워 두는 것이 정답이다

| 필드 | 왜 |
|---|---|
| `maintenanceFeeKRW` | 관리비는 실거래가 신고 항목이 아니다. **별도 출처 필요** |
| `marketRisk` | 원자료에 없는 **판단값**이다 |
| `guaranteeAvailable` | 보증기관의 **상품 조건**이지 시장 관측이 아니다 |

**배치는 이 셋을 건드리지 않는다.** 값도 계보도 이전 상태 그대로 둔다.
통계에서 유도하지 않고, 그럴듯한 값을 넣지 않는다.

여기에 국토교통부 이름이 붙는 순간 예시값이 실데이터인 척하게 된다 — SPEC 3.1 이
명시적으로 금지한 그것이다. 그래서 계보에서 이 셋은 시드의 「프로토타입 예시 데이터 /
`unverified`」를 그대로 들고 있고, 테스트가 국토부 이름이 붙지 않는 것을 고정한다.

---

### 5.1 계약해제된 매매는 세지 않는다

응답의 `cdealType` 이 `O` 면 **계약해제**다. 성사되지 않은 거래이므로 가격 중앙값에 섞으면
그 값은 「실거래가」가 아니게 된다.

**이것은 이상치 판단이 아니라 집계 대상의 정의다.** 6절의 「폐기 금지」는 *실제로 일어난*
거래를 함부로 지우지 말라는 규칙이고, 해제 건은 애초에 우리가 세려는 모집단이 아니다.

실측 — 마포구 3개월 표본 **206건 중 8건(3.9%)** 이 해제 건이었다 (2026-08-14).
필드 이름이 없는 응답에서는 **거르지 않는다.** 없다고 실패시키면 그 응답에서 전건이 죽고,
그 상태는 조용한 0건과 구분되지 않는다.


## 6. 이상치 — 표시하되 폐기하지 않는다

```
중앙값 × ratio 초과  또는  중앙값 ÷ ratio 미만   ->  이상치
ratio = ingest.market_outlier_deviation_ratio (= 3.0, our_choice)
```

검사 대상은 네 표본이다 — 전세 보증금 · 월세 보증금 · 월세 · 매매 거래금액.

- **집계에서 빼지 않는다.** 빼는 것도 폐기이며, SPEC 3 의 「자동 폐기 금지」를
  「집계에서 제외」로 우회하는 것이 가장 흔한 빠져나감이다.
- 이상치가 하나라도 있으면 그 지역의 도출 필드를 `unverified` 로 표시하고,
  **건별로** 감사기록(`market.outlier`)에 남긴다. 기록에 `discarded: false` 를 함께 적는다.

> **알려진 한계 (설계 발견, 튜닝 대상 아님).** `verification` 은 한 칸이므로
> 이상치로 인한 `unverified` 가 신선도의 `stale` 을 덮는다. 이상치가 걸린 지역에서는
> 이후 수집이 실패해도 `stale` 이 보이지 않는다. 필드별 계보로 쪼개도 이 충돌은 남는다 —
> 한 필드의 `verification` 칸이 여전히 하나이기 때문이다. 처리 방향은 코디네이터 판단 사항이다.

## 7. 계보 (SPEC 2.1 · 계약 결정 #4 · #12)

| | |
|---|---|
| `source_kind` | `market` |
| `source_name` | 필드마다 다르다. 파생 필드는 **산식의 출처와 우리 산출임**을 함께 적는다 |
| `source_ref` | 자료 제공 페이지 URL. **호출 URL 이 아니다** — 거기엔 키가 붙는다 |
| `observed_at` | **관측 기준시점** = 집계에 들어간 거래 중 **가장 늦은 계약일** (KST 00:00) |
| `fetched_at` | **우리가 취득한 시각** = 배치를 돌린 순간 |
| `verification` | 수집 성공 `verified` / 이상치 있음 `unverified` / 수집 실패 후 `stale` / 미도출 필드 이전 값 유지 |

시각은 RFC 3339 오프셋 포함이며 KST 는 `+09:00` 이다. **`Z` 표기를 쓰지 않는다** (결정 #4).

`observed_at` 을 수집 창의 마지막 달로 잡지 않고 **실제 거래일의 최댓값**으로 잡는 이유:
창은 2026-06~08 인데 마지막 거래가 6월이면, 창의 끝을 적는 순간 자료가 실제보다
두 달 신선해 보인다.

레코드 단위 `Region.provenance` 는 **필드별 계보의 최악값 요약**이다 (SPEC 2.4).
요약이 필드보다 좋으면 등급을 통과하려고 거짓말을 하는 것이므로, 저장소가 그 불변식을 건다.

## 8. 실패와 멱등

- **전건 성공일 때만 커밋한다.** 지역 하나가 실패했다고 나머지 아홉만 새 값이 되면
  그 저장소가 무엇을 뜻하는지 아무도 말할 수 없다.
- 실패하면 값은 하나도 바꾸지 않고, **이전에 수집에 성공했던(`verified`) 필드만** `stale` 로
  내린다. 출처가 없던 필드(`unverified`)를 `stale` 로 바꾸면 등급이 **좋아진다**(C → B) —
  실패를 이용해 데이터를 좋아 보이게 만드는 셈이다.
- **멱등:** 같은 입력·같은 배치 시각이면 저장소 상태가 그대로다. 시각이 다르면
  `fetched_at` 만 정직하게 달라지고 값과 `observed_at` 은 그대로다.
