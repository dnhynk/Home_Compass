# 코디네이터 운영 절차

SPEC 9.4(병렬 에이전트 작업 규칙)의 실행 형태. **SPEC 이 정본이고 이 문서는 절차다.**
충돌하면 SPEC 을 따르고 이 문서를 고친다.

## 왜 절차가 필요한가

SPEC Part 0-A 가 기록한 예선의 유일한 계약 사고는 **코디네이터가 계약을 바꾸고
한쪽에만 통지한 것**이었다. 즉 워커만 실패하는 게 아니라 코디네이터도 실패한다.
머지 판단이 매번 즉흥이면 그 실패가 재현된다.

## 루프

```
1. python scripts/coord_status.py                       ← 판단 재료를 모은다
2. orca orchestration check --wait --types worker_done,escalation,question \
       --timeout-ms 900000 --json                       ← 잠들지 않고 기다린다
3. 메시지 종류별 처리
     question      → orca orchestration reply --id <msg_id> --body <답>
     escalation    → 아래 「사용자에게 올리는 것」 판단
     decision_gate → 코디네이터가 답한다. 무응답은 승인이 아니다
     worker_done   → 4번으로
4. PR 심사 (아래 게이트)
5. 통과 → gh pr merge <n> --squash --delete-branch
   반려 → PR 에 코멘트로 반려 사유. 워커 터미널로 직접 재지시 (메일 아님, SPEC 9.4)
6. orca orchestration worker-release --dispatch <id>     ← 후속 과업이 없으면
   후속이 있으면 worker-start --task <next> --terminal <handle>
6-1. orca worktree rm --worktree name:<name> --force      ← 워크트리 정리
     git push origin --delete <branch> && git branch -D <branch>
7. main 의 CI 가 초록인지 확인 (PR CI 는 strict 가 아니라 구 base 에서 돌았을 수 있다)
8. 다음 파동 착수 조건 확인 → task-create → worker-start
9. check --ack <delivery_id> 후 2번으로
```

> ### ⛔ `check --ack` 를 단독으로 부르지 않는다 — 실측된 실패 경로
>
> **항상 `--ack <id> --wait --types ... --timeout-ms <n>` 한 번으로 부른다.**
> Orca 가 이 결합형을 제공하는 이유가 이것이다 — 확인과 재무장이 **갈라질 수 없게** 한다.
>
> 코디네이터가 이 실수를 **두 번** 했다. 둘 다 같은 모양이다 —
> `check --format` 이나 `check --ack` 로 한 번 보고, 재무장을 잊고, 턴을 끝냈다.
>
> | 회차 | 결과 |
> |---|---|
> | 1차 (kb-collect-2) | 워커의 `ask` 가 600초 타임아웃. 워커는 보류로 처리하고 PR 을 올렸으나 코디네이터가 **PR 이 올라온 것도 몰랐다** |
> | 2차 (kb-engines-4) | `ask` 1800초 타임아웃 → **task 가 `failed` 로 회로차단**. 워커가 **1시간 40분** 대기. `escalation` 2건과 `decision_gate` 까지 올렸는데 전부 안 읽혔다 |
>
> 두 번 다 **워커는 정상이었다.** 무응답을 승인으로 해석하지 않고 보류했고, 중복 질문도
> 만들지 않았다. 끊긴 것은 코디네이터 쪽뿐이다.
>
> ### ⛔ 결합형도 **처리보다 먼저 ack 하면** 같은 결과다 — 실측 (2026-08-15)
>
> 코디네이터가 대기를 스크립트로 감쌌다. 그 스크립트는 비하트비트 메시지를 **출력만 하고**
> 조건 없이 `--ack` 한 뒤 다음 대기로 들어갔다. 그래서 워커의 `question` 3건이
> **읽히지 않은 채 소비됐다.** 워커는 「답을 기다리는 동안 무관한 조립부를 먼저 만든다」로
> 정확히 대응했고, 끊긴 것은 코디네이터 쪽뿐이다 — 위 표의 두 사례와 **같은 모양**이다.
>
> 결합형은 [확인과 재무장이 갈라지지 않게] 하는 장치이지 **[처리했다]를 보장하지 않는다.**
> 자동화하면 그 사이에 사람 판단이 빠진다.
>
> **규칙:** ack 는 **처리 뒤**다. 대기 스크립트는 비하트비트 메시지가 있으면
> **거기서 멈추고 코디네이터에게 돌려준다.** 답한 뒤 다음 호출에서 ack 한다.
> 하트비트만 있을 때만 스크립트가 스스로 ack 해도 된다.

> **`--peek` 는 예외다** — 소비하지 않으므로 재무장 의무가 없다. 다만 `--peek` 로 본 것을
> 처리했다면 그 다음은 반드시 결합형이다.
>
> 그리고 **워커 하나를 띄우면 그 턴 안에서 대기를 건다.** 띄우고 보고만 하고 끝내면
> 위 두 경우가 그대로 재현된다.

**타임아웃은 실패가 아니다.** 코딩 과업은 15~60분이 정상이다. `check --wait` 가 빈
Delivery 를 돌려줘도 워커를 죽이지 않는다. 하트비트와 터미널 활동은 살아 있다는
뜻이지 끝났다는 뜻이 아니다.

> ### ⛔ 「살아 있다」는 「막히지 않았다」가 아니다 — 실측 (2026-08-15)
>
> 5단계 워커가 터미널 제목 `✳ <과업 제목>` 으로 유휴 상태였고 **하트비트는 계속 나갔다.**
> PR 도 `worker_done` 도 없었다. 터미널을 직접 읽고서야 원인이 나왔다 —
> **승인 프롬프트에 정지해 있었다.**
>
> ```
> Dangerous rm operation on working directory or its ancestor
>  ❯ 1. Yes    2. No
> ```
>
> 하트비트는 에이전트 루프가 보내는 것이지 진척에 걸려 있지 않다. 그래서 **막힌 상태와
> 오래 일하는 상태가 겉으로 같다.** 위 문단의 「하트비트는 살아 있다는 뜻」은
> 약하다 — **살아 있음이 곧 멈춰 있음일 수 있다.**
>
> **판정 규칙:** 워커가 `✳`(유휴)인데 **PR 도 `worker_done` 도 없으면** 생각 중이라고
> 읽지 말고 터미널 꼬리를 읽는다.
>
> ```bash
> orca terminal read --terminal <handle> --json     # result.terminal.tail
> ```
>
> 프롬프트면 선택지 번호를 터미널 입력으로 보내 답한다
> (`orca terminal send --terminal <h> --text '2' --enter`). 그리고 **왜 그렇게 답했는지**
> 를 이어서 알려 준다 — 거부만 하면 워커는 같은 것을 다시 시도한다.
>
> **지시서에 미리 적는다:** 「막히면 `ask` 를 올려라. 승인 프롬프트든 판단이든 상관없다.
> 하트비트만 보내며 기다리면 코디네이터는 네가 일하는 중이라고 읽는다.」

> ### ⛔⛔ `ask` 는 **터미널로 답할 수 없다** — 무인체계가 여기서 깨졌다 (2026-08-16)
>
> 워커의 `orca orchestration ask` 는 **차단 호출**이다. 조율 채널의 답을 기다리며 멈춰 있고,
> **터미널에 답을 찍어 넣는 것은 그 차단에 닿지 않는다.** 글자는 화면에 들어가지만 워커는
> 타임아웃까지 그대로 서 있다. 그동안 **하트비트는 계속 나가므로** 코디네이터 쪽에서는
> 「일하는 중」으로 보인다 — 위 문단의 함정과 같은 모양인데 **원인이 코디네이터 자신**이다.
>
> ```bash
> orca orchestration inbox --json      # type=question · read=0 인 것의 id
> orca orchestration reply --id <msg_id> --body <text> --json
> ```
>
> **이 세션에서 세 번 물렸다** (900s · 900s · 1800s). 「내가 느려서 재웠다」고 세 번 적었는데
> **사실이 아니었다 — 답이 그 채널로 간 적이 없었다.** 워커 하나는 「중복 질문을 만들지
> 않으려」 재질의를 포기했고 판단 2건이 `worker_done` 까지 미해결로 갔다.
> **증상을 원인으로 오인하면 세 번 같은 자리에 선다.**
>
> ★ `--body` 에 **ASCII `"` 를 넣지 마라.** PowerShell 에서 인자가 그 자리에서 끊기고
> `Unknown command` 라는 엉뚱한 오류가 난다. 한국어 따옴표(`「」` · `『』`)로 바꿔 쓴다.
>
> **터미널 `send` 를 쓰는 자리는 따로 있다** — 승인 프롬프트 응답(위 문단), 그리고 `ask` 가
> 아닌 **추가 브리핑**이다. 워커가 무언가를 기다리고 있다면 그건 언제나 조율 채널이다.

## 머지 게이트

### 기계가 확인한다 (상태판 + CI)

1. **CI 통과** — 워커의 "테스트 통과했습니다"는 근거가 아니다 (SPEC D-10)
2. **소유 경로 준수** — SPEC 9.4 배정표 밖의 파일을 건드리지 않았는가
3. **계약 파일 무변경** — `contracts/` · `backend/tests/crosscheck/` ·
   `docs/engineering/SPEC.md` 는 코디네이터만 바꾼다 (SPEC 8.2 #5)
4. **충돌 없음**

### 사람이 읽는다 (자동화하지 않는다)

5. PR 본문에 **SPEC 9.3 여섯 항목의 답**이 있는가
6. ③ "돌려봤다"에 **명령어와 그 출력**이 첨부되었는가.
   첨부되지 않았으면 미검증으로 간주한다 (SPEC 9.3)
7. ⑥ **검증하지 않은 것**이 비어 있으면 **반려한다.** 비어 있는 경우는 사실상 없다
8. 새 상수에 **Provenance** 가 붙었는가 (SPEC 9.3 #5)
9. **값을 지어내지 않았는가** — 실사 미정 항목을 그럴듯한 수치로 메웠는지.
   이게 이 프로젝트의 지배적 실패 양상이다 (SPEC Part 0-C)

> 5~9 중 하나라도 걸리면 기계 게이트를 통과했어도 반려한다.
> 반려는 실패가 아니라 게이트가 작동한 것이다.

> **경로를 처음 등재하는 변경은 그 경로를 쓰는 변경보다 먼저 머지한다.**
>
> 게이트는 **`main` 의 `WORKER_PATHS` 로 판정한다.** 그래서 배정표에 없던 경로를
> 「등재 + 사용」 한 PR 에 담으면 **구조적으로 통과할 수 없다** — 판정 시점에는
> 아직 등재 전이기 때문이다. PR #87(README.md)이 여기 걸렸다.
>
> 게이트가 PR 쪽 표를 읽게 고치는 방법도 있으나 **그러지 않는다.** 표를 정본으로
> 삼는 것이 게이트를 믿을 수 있게 만드는 성질이고, PR 이 자기 판정 기준을 함께
> 들고 오면 그 성질이 사라진다. 대신 **두 PR 로 나눈다** —
> ① 등재만 (`scripts/coord_status.py`) → ② 그 경로의 실제 변경.
>
> SPEC 9.4 의 마지막 줄이 같은 말을 이미 하고 있다:
> 「두 소유자가 걸리는 변경은 코디네이터가 **순서를 정해 직렬로** 낸다.」

> **★ 워커를 회수할 때, 그 워커만 갖고 있던 경로가 무주공산이 되는지 본다.**
>
> **두 번 물렸다.** `W-admin` 을 지우자 `README.md` 가 주인을 잃어 PR #87 이 막혔고,
> `W-rehearsal` 을 지우자 `REHEARSAL.md` 가 그렇게 돼 PR #95 가 막혔다. 둘 다 위의
> 「등재 PR 을 먼저」로 풀렸지만 **회수 시점에 봤으면 없었을 왕복**이다.
>
> 회수는 두 동작이다 — **① 워커를 지운다 ② 그 워커의 경로 중 남는 주인이 없는 것을 찾아
> 옮긴다.** ②를 빼먹으면 다음 PR 이 그 자리에서 걸린다. 확인은 이 한 줄이면 된다:
>
> ```
> python -c "import sys; sys.path.insert(0,'scripts'); import coord_status as c; \
>   [print('무주공산:', p) for p in <지우는 워커의 경로> \
>    if not any(p.startswith(q) or q.startswith(p) for w in c.WORKER_PATHS.values() for q in w)]"
> ```

## 계약 변경 절차 (SPEC 8.2)

워커는 `contracts/` 를 고치지 못한다. 필요하면 `ask` 로 요청한다.

1. 워커의 `ask` 를 받는다
2. 코디네이터가 `contracts/` 를 고친다 — **코디네이터만** (8.2 #5)
3. 변경 근거를 파일 안 `$comment` 와 `contracts/README.md` 에 남긴다
4. **영향받는 전원에게 전파한다.** 한쪽에만 통지하는 것이 예선의 사고였다
5. 전파는 **터미널로 직접** 한다 — `orca terminal send`.
   orchestration 메일은 워커가 `check` 를 부르지 않으면 읽지 않는다 (SPEC 9.4)

- 신규 (d) `our_choice` 상수의 초기값 선정 (감도분석 대상에 자동 포함되므로 되돌리기 쉽다)
- 계약 파일 변경
- 실패한 워커의 재dispatch · 과업 재분할

**사용자에게 올린다:**

| 대상 | 왜 |
|---|---|
| **범위 결정** — 수집 대상(어느 기관의 어떤 공고문 몇 건) · 대상 지역 수 · 정책 건수 · 공고문 원문 크기 상한 · 합성 프로필 세트 개수 | 조사가 아니라 제품 결정. SPEC 실사 목록 C |
| **(a)(b)(c) 상수의 `verified` 승격** | 틀린 숫자가 전 판정에 퍼진다. 리서처의 인용표를 사용자가 보고 승인 |
| **SPEC 본문 변경** | SPEC 은 계약서다 |
| **비용·외부 노출** — LLM API 지출, 저장소 공개, 유료 플랜 | 사용자 자산 |
| **SPEC 의 두 조항이 실제로 충돌해 한쪽을 버려야 할 때** | 경계 고정이 아니라 취사선택이면 코디네이터 권한 밖 |

## 파동 (SPEC Part 10 의 거울)

`scripts/coord_status.py` 의 `WAVES` 가 기계 판독본이다. 정본은 SPEC Part 10.

| 파동 | 내용 | 선행 |
|---|---|---|
| W1 | 0단계 저장소 ∥ 1-① 엔진 구조 ∥ 실사 | — |
| W2 | W-platform — 계약 생성기 · 부팅 전수검증 · 교차 테스트 | W1 |
| W3 | 2단계 정책 추출 ★ 사용자 결정 선행 | W2 |
| W4 | 3단계 시세 · 4단계 인증·권한 | W2 |
| W5 | 5단계 규칙 관리 화면 · 6단계 판정 화면 확장 | W3, W4 |
| W6 | 6-A 이상 신고 · 7단계 감사·관측 · 8단계 리허설 | W5 |

**순차 완성 원칙(SPEC Part 10)을 어기지 않는다.** 단계 간 병렬은 금지고,
단계 안에서 소유 경로가 분리된 작업만 병렬로 낸다. 0단계와 1-① 의 병렬은
SPEC 이 명시적으로 허용한 유일한 조합이다.

**중단 규칙.** 기간이 부족해지면 3단계(시세)를 수동 갱신으로 축소하고
2단계(정책 추출)를 완성한다. 정책 추출이 본선의 기술적 중심이다.

## 머지 후 정리 — 반복해서 쓸 것이 아니면 남기지 않는다

`gh pr merge --delete-branch` 는 **Orca 워크트리가 브랜치를 체크아웃하고 있으면 조용히 실패한다.**
실제로 워커 브랜치 9개와 워크트리 9개가 그렇게 쌓였다. 상태판이 그것을 보지 않으므로
쌓이는 것을 아무도 모른다.

**워커 PR 을 머지한 직후 같은 턴에서 정리한다:**

```bash
orca worktree rm --worktree name:<worktree-name> --force --json
git push origin --delete <branch>
git branch -D <branch>
git worktree prune
```

> ⚠️ **`git branch --merged` 로 판단하지 마라.** squash 머지는 원본 커밋을 main 의 조상으로
> 만들지 않으므로 머지된 브랜치가 `--no-merged` 로 나온다. **정본은 PR 상태다** —
> `gh pr list --state all --json headRefName,state` 로 확인한다.

정상 상태는 **`main` + 열린 PR 브랜치뿐**이다.

## 이 환경의 알려진 함정

| 함정 | 대응 |
|---|---|
| `main` 브랜치 보호 불가 (Free 플랜 private) | `.githooks/pre-push` + 코디네이터 머지 절차. `--no-verify` 로 우회 가능함을 인지한다 |
| PowerShell 이 인자 안의 `"` 를 구분자로 먹는다 | 워커 지시서에 `"` 를 쓰지 않는다. `'` 를 쓴다 |
| `worker_done` 이 `dispatch_capability_invalid` 로 거부될 수 있다 | Orca 가 run 메일함에 원문을 보존한다. 워커에게 평문 `send --to run:<id>` 폴백을 지시해 둔다 |
| Orca 가 브랜치명을 `dnhynk/<name>` 으로 정한다 | 지시서의 브랜치명과 다를 수 있다. PR 기준으로 추적한다 |
| PR CI 가 구 base 에서 돌 수 있다 (strict 미적용) | 머지 후 `main` 의 CI 를 확인한다 |
