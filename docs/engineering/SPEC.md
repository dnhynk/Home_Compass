## Part 0. 범위 결정 기록 (확정)

예선 산출물 감사에서 드러난 공백은 네 개였다 — 데이터 연동 · 영속성 · 인증 · 관측성.
논의 결과 이 넷은 독립 항목이 아니라 **하나의 덩어리**였음이 확인되었고, 본선 범위에 전부 들어온다.

### D-1. 데이터 연동 — 두 파이프라인 모두 구축

| | 결정 | 근거 |
|---|---|---|
| 시세 | 공공 API 연동 | 배관 문제. 난이도 낮고 "실데이터"를 즉답 가능 |
| 정책 | 공고문 → 판정 규칙 **추출** | API가 없음. 자격 요건이 자연어 |

**핵심 인식:** 둘은 성격이 다른 문제다. 시세는 *연동*, 정책은 *변환*이다.
정책 쪽이 본선의 기술적 중심이다 — LLM이 실제로 값을 하는 유일한 지점이고,
"LLM은 말하고 숫자는 엔진이" 라는 기존 아키텍처 철학의 자연스러운 확장이다:

> **LLM이 규칙 초안을 쓰고, 사람이 승인하고, 엔진이 집행한다.**
> 승인되지 않은 규칙은 판정에 절대 반영되지 않는다.

**리스크(기록용):** 범위가 두 배다. 이 리스크는 코디네이터가 제기했고 채택되었다.
완화책은 **순차 완성** — 병렬로 반쯤씩 짓지 않고 하나를 끝낸 뒤 다음으로 간다.
기간이 부족해질 경우 "둘 다 미완"이 아니라 "하나는 완성"으로 끝나야 한다.

### D-2. 신선도 — 정기 수집 후 저장

요청 시 실시간 조회가 아니라 배치 수집 + 저장.
→ **저장소가 본선 범위에 포함된다.** 외부 API 장애가 서비스 장애로 전파되지 않는다.

### D-3. 승인자 — 은행 실무자 (관리자 화면)

개발자 리뷰가 아니라 비개발자용 검토·승인 화면을 만든다.

**연쇄:** 승인 권한이 있는 화면은 무인증으로 열 수 없다 → **인증 포함.**
승인 이력이 곧 감사추적이다 → **관측성의 핵심 포함.**
이 결정 하나가 남아 있던 공백 둘을 동시에 소진했다.

### D-4. 커버리지 — 서울 중심, 좁고 깊게

지역을 좁히는 대신 데이터 품질을 끝까지 끌어올린다.
틀린 숫자로 판정하는 사고를 줄이고, 넓어진 범위를 감당할 여지를 만든다.

> ### ⚠️ 정정 (2026-08-14, 사용자 승인) — 시세 **수집 대상**은 현행 지역 10건 전부다
>
> 이 결정의 취지(**품질 우선**)는 유지된다. 바뀌는 것은 시세 수집이 도는 지역 목록뿐이다.
>
> **왜.** `regions.json` 은 부트스트랩부터 10건이었다 — 서울 4 · 경기 2 ·
> 부산·대전·대구·광주 4. 「서울만 수집」을 문자 그대로 집행하면 **비서울 6건이 영원히
> 예시값으로 남고**, 같은 산출물 안에 진짜와 예시가 섞인다. 3.1 이 금지하는 것은
> 「예시값을 실데이터인 척 두는 것」인데, 한쪽만 수집하면 그 상태가 **구조적으로 고정된다.**
>
> **그리고 비서울 지역을 지울 수도 없다.** F-4(수도권/비수도권 가입요건 상한)의 분기와
> `guaranteeAvailable=False` 경로를 회귀에서 덮는 것이 부산·광주 지역이다
> (`contracts/regression_profiles.json` 의 `non_metro` · `non_metro_no_guarantee`).
> 지우면 그 두 분기의 골든 커버리지가 함께 사라진다.
>
> **비용은 호출 수뿐이다.** 실거래가 API 는 지역코드가 파라미터라 지역이 늘어도
> 구현 난이도는 사실상 같다. D-4 가 막으려던 것은 **품질을 희생한 확장**이지
> 이미 들고 있는 데이터를 실측으로 바꾸는 일이 아니다.

### D-5. 데이터 신뢰 — 거부하지 않고 등급을 붙인다

낙후·미승인 데이터라도 판정은 수행하되,
**"이 숫자는 언제 · 어느 출처 기준이며 검증 상태는 무엇인지"** 를 함께 노출한다.

**의미:** 예선에서는 *판정*에만 근거가 붙고 *입력 데이터*에는 근거가 없었다.
이 결정으로 그 구멍이 메워지고 설명가능성이 완성된다.
데이터 계보(출처 · 수집시각 · 검증상태)는 저장소에서 판정 결과를 거쳐 화면까지 끊기지 않고 전달되어야 한다.

### D-6. 판정 모델 — 재무 모델 재설계

예선 엔진은 근거 없는 상수로 동작한다. 감사에서 확인된 것 중 일부:

| 상수 | 현재 값 | 문제 |
|---|---|---|
| 연봉 → 월 실수령 | `×0.85` 단일 계수 | 4대보험·소득세 구간 무시 |
| 할인율 / 기회비용률 | `3.0%` 고정 | 기간구조·인플레·세금 미반영 |
| 주거비 상한 비율 | `30%` | 관행적 기준, 근거 미상 |
| 1인 가구 생활비 | `120만원` 하드코딩 | 출처 없음 |
| 리스크 구간 경계 | `34 / 64` | 통계적 근거 없음 |

진짜 데이터를 붙이는 순간 이 부분이 가장 약한 고리가 된다.

**⚠️ 미결 (다음 회차 안건):** 이 작업은 코딩이 아니라 **근거 조사**다.
무엇을 정답으로 삼을지 — 어떤 공표 통계 · 어떤 산식을 기준으로 채택할지 — 를
먼저 합의해야 한다. 합의 없이 에이전트를 풀면 그럴듯한 숫자를 지어낸다.
이는 예선에서 지킨 데이터 정직성 원칙에 정면으로 위배된다.

### D-7. 예산

기간 1개월 이상 · 인력은 병렬 에이전트 + 사람 1인(의사결정·검토).

**제약이 이동한다.** 시간이 병목이 아니게 되면 병목은
"얼마나 만드느냐"가 아니라 **"만든 것을 어떻게 믿느냐"** 가 된다.

## Part 0-A. 이 문서가 계약서여야 하는 이유 (예선 실측 근거)

예선 하루 동안 에이전트 6대를 병렬로 돌렸다. 실제로 발생한 결함은 대부분 한 유형이었다.

| 발생한 결함 | 유형 |
|---|---|
| 백엔드가 응답 계약을 바꿨는데 프론트가 몰라 상태 배지 오표시 | 계약 드리프트 |
| **채팅** 프론트 타임아웃(4.5초) < 실제 응답(2.7~6.9초) → 조용히 폴백 | 경계 조건 미합의 |
| 같은 금액을 백엔드는 내림, 프론트는 반올림 (80만 vs 81만) | 규칙 미합의 |
| 1순위 프로바이더인 `openai`가 의존성 목록에서 누락 | 통합 미검증 |
| 실행 스크립트가 인코딩 문제로 파서 붕괴 | 실행 미검증 |

전부 **"각자는 맞는데 합치면 틀린"** 유형이다.
에이전트는 서로 대화하지 않으므로 이는 우연이 아니라 구조적으로 발생한다.

**따라서 이 스펙은 다음을 명시적으로 고정해야 한다:**
1. 시스템 경계마다의 **데이터 계약** (필드명 · 타입 · 단위 · 반올림 규칙)
2. **경계 조건** (타임아웃 · 재시도 · 실패 시 동작)
3. 계약 변경 시 **누구에게 전파되어야 하는지**
4. 각 작업의 **완료 판정 기준** — "돌려봤다"의 정의

예선에서 유일하게 어긋난 계약은 **중간에 코디네이터가 계약을 바꾸고 한쪽에만 통지한** 지점이었다.
계약 변경 전파는 문서가 아니라 절차로 강제되어야 한다.

## Part 0-B. AI 활용 지점의 정의와 경계 (확정)

### 두 가지 AI 사용은 같은 것이 아니다

본 제품에서 LLM은 두 가지 **성격이 다른 방식**으로 쓰인다.
같은 "LLM 사용"으로 묶어 같은 대책을 적용하면 둘 다 실패한다.

| | **A. 런타임 에이전트** | **B. 오프라인 추출** |
|---|---|---|
| 트리거 | 사용자 입력 | 배치 / 새 공고문 감지 |
| 제어흐름 | 하네스가 루프, 모델이 다음 행동 결정 (비결정적) | 단발 변환, 결정적 파이프라인의 한 단계 |
| 출력의 성격 | **답변 (문장)** | **데이터 (기계 판정 규칙)** |
| 자동 검증 | 사실상 불가 | **가능** — 스키마 검증 + 사례 테스트 |
| 출력 소비자 | 사용자에게 직행 | 사람 검토자 → 규칙 저장소 |
| 검증 시점 | 사후 | **사전** (승인 전 효력 없음) |
| 실패 반경 | 한 번에 **한 명** | 한 번에 **전원** |

**B를 이해하는 올바른 비유는 에이전트가 아니라 컴파일러다.**

> 자연어 공고문 = 소스코드 · 판정 규칙 = 목적코드 · 사람 승인 = 코드리뷰 · 규칙 테스트 = CI

**방어 방식이 정반대여야 한다:**
- A는 자주 틀리지만 한 명에게 → **숫자 생성 권한 박탈** (엔진 반환값만 인용)
- B는 드물게 틀리지만 전원에게 → **사람 게이트 + 회귀 테스트**

### 확정된 AI 활용 지점 — 전 2곳 (+ 검토 보조)

| # | 지점 | 유형 | 결정 |
|---|---|---|---|
| 1 | 런타임 상담 채팅 | A | **채택.** 유일한 런타임 AI. 숫자 생성 권한 없음 |
| 2 | 공고문 → 판정 규칙 추출 | B | **채택.** 본선의 기술적 중심 |
| 6 | 관리자 검토 보조 (원문 근거 매핑) | B 부속 | **채택.** 아래 게이트 요건 참조 |
| 3 | 판정 요약문 생성 | — | **미채택.** 결정론적 유지 |
| 10 | 리스크 설명문 생성 | — | **미채택.** 결정론적 유지 |
| 8 | 자연어 프로필 입력 | A | **미채택.** 입력이 틀리면 전 판정이 틀린다 |
| 4 | 공고문 수집·선별 | — | **미채택.** 출처·키워드 룰로 충분 (서울·소수 기관) |
| 5 | 규칙 변경 diff 해석 | — | **미채택.** 결정론적 diff + 회귀 테스트가 더 낫다 |
| 7 | 시세 이상치 탐지 | — | **미채택.** 통계로 처리 |
| 9 | 정책 검색·임베딩 | — | **미채택.** 현 규모에 과잉 |

> **범위 밖:** 개발에 병렬 에이전트를 쓰는 것은 제품 기능이 아니다.
> 참가신청서 AI 활용표에 기재한 것은 이쪽이며, 위 목록과 혼동하지 않는다.

### 이로부터 나오는 아키텍처 원칙

**원칙 1 — 판정 경로에 AI가 없다.**
`/api/analyze` 는 LLM을 호출하지 않는다. 동일 입력은 항상 동일 출력을 낸다.
LLM 장애나 API 키 부재가 핵심 판정 기능을 건드리지 못한다.

**원칙 2 — AI 산출물은 사람 승인 없이 판정에 반영되지 않는다.**
추출된 규칙은 승인 전까지 저장소에서 격리되며 어떤 사용자 판정에도 참여하지 않는다.

**원칙 3 — 사람 게이트는 형식이 아니라 실질이어야 한다.**
검토 화면은 다음을 반드시 제공한다. 이것이 없으면 승인은 거수기가 된다.
- 추출된 규칙 각 필드에 대해 **근거가 된 원문 구간** 대조 표시
- 승인 시 **기존 판정이 어떻게 바뀌는지**를 실제 사례로 제시 (회귀 테스트)

**잔존 리스크 (과장하지 않기 위해 명시):**
원칙 1·2에도 불구하고, 채팅(#1)이 엔진 반환값을 **문장으로 옮기는 과정에서 오인용**할 여지는 남는다.
판정 자체는 오염되지 않으나 화면에 표시된 문장은 틀릴 수 있다.
이에 대한 방어(툴 결과 인용 강제 및 검증)는 8절에서 다룬다.

## Part 0-C. D-6 확정 — 모델 상수의 출처 기준 (5절 차단 해제)

### 원칙

**"재무 모델의 정답"은 단일 출처에서 오지 않는다.**
상수의 성격에 따라 정답의 종류가 다르며, **성격을 혼동하는 것이 가장 치명적인 오류**다.

| 유형 | 성격 | 출처 | 처리 |
|---|---|---|---|
| **(a)** | 법정 계산 | 법령·고시 | 정답 존재. **추정 금지, 계산으로 대체** |
| **(b)** | 관측 통계 | 공표 통계 | 인용 + **기준시점 명시** |
| **(c)** | 시장 가격 | 공표 금리 | 관측값 + **기준일 명시**, 만기 대응 |
| **(d)** | 규범적 선택 | 준거가 있으면 인용 | **정답 없음.** 우리 선택임을 명시 + 감도분석 |

> **핵심 규율: (d)를 (a)(b)(c)인 척하지 않는다.**
> 가정을 없애는 것이 목적이 아니라 **가정임을 밝히고 정당화하는 것**이 목적이다.

**근거 — SR 11-7** (미 연준·OCC, 2011-04-04, *Supervisory Guidance on Model Risk Management*):
모델 문서는 모델을 모르는 제3자가 코드 없이 재현할 수 있을 정도로 상세해야 하고, 설계·이론·논리가
공표된 연구 및 건전한 업계 실무와 일치해야 하며, **모든 기저 가정이 문서화·정당화**되어야 한다.

>
> **정정 2 — 「청년 RIR이 3배 이상 벌어진다」는 재현되지 않는다.**
> 2024년도 조사에서 원문확인한 모집단별 중위수는 다음과 같다.
>
> | 모집단 | RIR 중위수 |
> |---|---|
> | 전국 임차가구 | 15.8% |
> | **수도권 임차가구** | **18.4%** |
> | 광역시 등 / 도지역 | 15.2% / 12.7% |
> | 청년가구(가구주 만19~34세) 임차 | 16.0% |
> | 신혼부부(혼인 7년 이하) / 고령가구 | 17.7% / 25.4% |
>
> **소득계층별도 확인됐다** (2차 실사 R5 — 연구보고서 p.101). 보도자료에는 없고
> 546면 통계보고서에도 없으며, 195면 **연구보고서**에 있었다.
>
> | 소득계층 | RIR 중위수 |
> |---|---|
> | 하위 | 18.3% |
> | 중위 | 16.2% |
> | 상위 | 19.4% |
>
> **최대·최소 비는 19.4 / 15.8 ≈ 1.23배다.** 어느 두 모집단을 잡아도 3배가 되지 않는다.
> 평균 기준으로 넓혀도 24.1 / 20.2 ≈ 1.19배다. **이 서술은 인용하지 않는다.**
>
> **✅ RIR 은 DSR 과 달리 준거로 쓸 수 있다.** 연구보고서 p.54 원문 —
> 「소득은 세금 등을 제외한 **월평균 실수령액**을 조사한 결과」.
> 우리 `housing_cost_ratio_cap` 의 분모(월 실수령액)와 **정의가 같다.**
> DSR 을 기각한 이유(분모가 세전 연소득)가 여기에는 해당하지 않는다.
> 다만 **분자**(월임대료 — 보증금을 월세이율로 환산)가 우리 `monthlyHousingCost` 와
> 같은 정의인지는 아직 확인하지 않았다.
>
> **채택된 준거:** `affordability.housing_cost_ratio_cap` 은 **수도권 임차가구 18.4%** 를
> 준거로 인용하되, 상한값 `0.30` 은 관측 중위수가 아니라 **허용 최대치인 우리 선택**임을
> 함께 밝힌다. 30% 라는 수치 자체에는 공표 준거가 없다. (`contracts/README.md` 결정 #8)

### 분류 중 발견된 모델 결함 (신규)

**F-1 — 슈바베지수가 상수의 되풀이다.**
```python
recommended = min(max_cost * RECOMMENDED_HAIRCUT, net_income * RECOMMENDED_RATIO_CAP)
schwabe     = recommended / net_income     # 비율 상한이 걸리면 항상 정확히 25.0%
```
슈바베지수는 통상 **실제 주거비 / 소득**이다. 현재 구현은 **권장 주거비 / 소득**이라,
비율 상한이 걸리는 대다수 경우 `RECOMMENDED_RATIO_CAP`을 그대로 되돌려준다.
실측에서 `750,000 / 3,000,000 = 25.0%`가 나온 것은 우연이 아니다.
**측정값을 가장한 상수이며, 사용자에게 아무 정보도 주지 않는다.**
→ 사용자가 검토 중인 실제 시나리오 기준으로 재정의할 것.

**F-2 — 권장액 상한 두 개가 서로를 가린다.**
`0.30 × 0.85 = 0.255` vs `0.25`. 근거 없는 규범 상수 둘이 2% 차이로 겹친다.
구간에 따라 각각 유효해지므로 죽은 코드는 아니나, **어느 쪽도 정당화되지 않은 채 중복 작동**한다.
→ 정당화 가능한 단일 규칙으로 통합.

### 산출물 요구사항 — 가정 계보

D-5에서 *데이터*에 출처·수집시각·검증상태를 부여하기로 했다.
**모델 상수에 동일한 계보를 부여한다.**

각 상수는 다음을 함께 보유한다: `유형(a~d)` · `출처` · `기준시점` · `우리 선택 여부`.
이로써 판정 결과 하나에 대해 **"어떤 데이터와 어떤 가정에서 나왔는가"** 를 끝까지 추적할 수 있다.
이는 SR 11-7이 요구하는 제3자 재현 가능성과 동일한 요건이다.

## Part 0-D. 추가 확정 사항

### D-8. 실행 형태 — 로컬 시연 확정, 배포는 문서 증명

본선은 **오프라인 발표·시연**이다. 무대에서 도는 것은 발표자 노트북이며,
심사위원이 코드를 받아 직접 실행하는 순간은 없다.

- **시연 경로는 로컬 단일 호스트로 확정한다. 네트워크 의존을 금지한다.**
  현장 Wi-Fi 장애가 시연 전체를 무너뜨리는 구조를 만들지 않는다.
- 배포 가능성은 **설계와 문서(부록 A)로 증명**한다. 저장소·설정을 교체 가능하게 두되
  실제 배포는 필수가 아니다. 배포하더라도 **시연 경로로 삼지 않고 보조 증빙으로만** 둔다.

핵심 시연 장면(승인 → 시민 화면 변화)은 노트북 한 대에서 창 두 개로 성립한다.

### D-9. 역할 3종 · 화면 2개 (역할 분리 ≠ 화면 분리)

| 역할 | 하는 일 | 규칙 변경 |
|---|---|---|
| **시민** (익명) | 셀프 판정 | ✕ |
| **상담원** (영업점) | 고객 앞에서 판정 도구 사용, 근거를 상담에 활용 | **✕** |
| **규칙관리자** (본부) | 추출 규칙 검토·승인 | ○ |

**화면은 둘뿐이다.**
- **판정 화면 (하나)** — 익명이면 시민 모드, 로그인하면 상담원 확장(내부 정보 + 요약본 출력)이 켜진다.
- **규칙 관리 화면 (별개)** — 하는 일 자체가 판정이 아니라 검토·승인이므로 분리가 정당하다.

> **판정 화면을 역할별로 포크하지 않는다.** 95% 동일한 화면 두 벌은 반드시 갈라지며,
> 그것이 Part 0-A에 기록된 실패 유형이다.
> **권한 분리(SoD)는 권한 계층에서 강제하는 것이지 화면을 나눠서 얻는 것이 아니다.**

### D-10. 검증 엄격도 — 최상위 (9절)

Part 0-A의 실패 유형마다 **깨지면 빨간불이 켜지는 장치**를 둔다. 규율이 아니라 구조로 막는다.

## Part 0-E. 미결 4건 확정 · 표준 채택 · 채우지 않은 것 (2026-08-13 2차)

계약 감사에서 **"에이전트가 추측으로 메울 수밖에 없는 지점"** 이 다시 식별되었다.
아래 넷은 결정했고, 나머지는 **공인 표준으로 채우거나 실사로 승격**했다.
**둘 중 어느 쪽도 아닌 것을 그럴듯한 값으로 채우는 것을 금지한다.**

### D-11. 프론트엔드 판정 사본 — 생성물로 동기화

`frontend/app.js` 에는 판정 엔진 **사본**이 있다 (`POLICY_CATALOG` · `engineAffordability` ·
`engineScenarios` · `enginePolicies` · `engineRisk` · `engineVersion: '1.0.0-frontend-fallback'`).
자체 상수(연소득 5천만 · 30% 상한 · 버퍼 · 슈바베)를 백엔드와 **별개로** 갖는다.
예선 스펙은 이 경로의 존재를 한 번도 언급하지 않았다.

**결정: 유지하되 손으로 쓰지 않는다. 백엔드·저장소에서 생성한 산출물로 대체한다.**

- 이 경로가 쓰는 상수·정책 규칙은 **`ModelConstant` 와 승인된 `RuleVersion` 에서 생성**된다.
  판정의 단일 출처가 유지되고, 2.3(승인 게이트)·5.1(리터럴 금지)이 이 경로에도 걸린다.
- 생성물은 **손으로 수정하지 않는다.** 재생성 diff 테스트로 강제한다(D-12와 같은 장치).
- 생성물이 없거나 낡으면 이 경로는 **동작하지 않는다.** 침묵 폴백을 금지한다 —
  조용한 폴백은 Part 0-A에 기록된 실패 유형 그 자체다.
- 6.2의 "오프라인 동작 보존"이 가리키는 것은 **이 경로**다. 정의를 6.2에 고정한다.

> 비용은 생성 파이프라인 하나다. 대신 2.3 · 5.1 · 9.1이 프론트에도 자동으로 적용된다.

### D-12. 계약 파일 — 코드에서 생성 + 재생성 diff

- **위치·형식** `contracts/openapi.json` — OpenAPI 3.1 (JSON Schema 2020-12). `api` 가 생성한다.
- **강제** 테스트가 앱에서 스키마를 재생성해 커밋본과 **바이트 비교**한다.
  코드만 바꾸면 깨진다(8.2 #2). 계약을 바꾸면 서버 스키마 테스트와 클라이언트 생성물 테스트가
  **동시에** 깨진다(8.2 #3).
- **단위 · 반올림 · 타임아웃 · 재시도**는 `x-` 확장으로 **같은 파일**에 담는다(8.2 #4).
- **클라이언트 소비** 같은 파일에서 평문 JS 상수 모듈을 생성해 커밋한다.
  빌드툴·CDN 없이 `<script>` 로 읽힌다(6.2 유지). D-11 생성물과 같은 파이프라인이다.
- 스모크 테스트의 합격 판정은 이 파일 기준이다(9.1).

### D-13. 계보의 응답 형태 — 최상단 요약 1개 + 사실 단위 목록

`/api/analyze` 응답에 다음을 싣는다. **기존 필드는 그대로 둔다**(8.1).

  그 사실이 근거짓는 응답 위치를 **JSON Pointer**(RFC 6901) 목록으로 가리킨다.

  화면 문구 용도이고, **기계 판독의 정본은 `provenance`** 다. 이 관계를 계약 파일에 적는다.

### D-14. 1단계 3분할 — 구조 작업은 실사에 막히지 않는다

5절은 성격이 다른 셋을 한 단계로 묶고 있었다. 실사에 막히는 것은 ②뿐이다.

| 하위 단계 | 내용 | 선행 |
|---|---|---|
| **1-①** 구조 | 상수 외부화 · `ModelConstant` · 주입 경로 · 리터럴 검사 · 감도분석 골격 | 0단계와 병렬 |
| **1-②** 값 | (a) 법정 산식 대체 · (b)(c) 실수치 반영 | **잔여 실사 확정** |
| **1-③** 로직 | F-1 슈바베 재정의 · F-2 상한 통합 | 1-① |

**1-①은 값을 모르는 채로 완료할 수 있다.** 상수는 저장소에 자리만 만들고
**현행 값을 `unverified` 로 등재**한다. 판정 결과는 바뀌지 않고, 등급이 정직하게 `C` 가 된다.
값이 확정되면 1-②가 **데이터만 갈아끼운다. 코드는 다시 바뀌지 않는다.**

### 공인 표준으로 채운 것 (추측 아님)

| 공백 | 채택 | 근거 |
|---|---|---|
| span 오프셋 정의 | **NFC 정규화 후 코드포인트 오프셋.** 대상은 `PolicySource` 에 저장된 추출 텍스트 | Unicode UAX #15 |
| `field_path` 표기 | **JSON Pointer** | RFC 6901 |
| `RuleDraft` · 계약 스키마 형식 | **JSON Schema 2020-12**, `additionalProperties: false` | OpenAPI 3.1 채택판 |
| 비밀번호 저장 | **Argon2id** (`argon2-cffi`) | OWASP Password Storage CS |
| 세션 · CSRF | 서버 세션 + `HttpOnly`·`SameSite` 쿠키, 상태변경 요청에 CSRF 토큰 | OWASP ASVS · CSRF CS |
| 응답 스키마 검증 | 계약 파일 기반 자동 검증(예: schemathesis) | OpenAPI 생태계 |
| 시각 의존 배제 | 클럭 주입 + 테스트에서 고정 | 결정성 테스트 통상 기법 |

### 표준이 없어 코디네이터가 정한 것 (이견 시 8.2 절차)

1. **역할별 응답 분기 없음.** `/api/analyze` 는 하나의 스키마를 갖고, 6.1의 내부 정보는
   **인증된 요청에만 채워지는 부가 필드**로 실린다. 별도 엔드포인트로 나누면 같은 판정을 두 번
   계산하게 되고 둘이 어긋날 수 있다. 계약 파일에 `x-requires-role` 로 표기하고,
   **익명 응답에 해당 필드가 없음**을 권한 테스트로 고정한다(9.2 #3).
2. **상수 조회 실패 = 기동 거부.** 런타임 기본값을 두지 않는다. 기본값을 허용하면 5.1이 무너진다.
   필수 상수 전수 존재를 **기동 시** 검증하고, 없으면 뜨지 않는다(fail-closed).
3. **`dataGrade` 산정에서 `our_choice` 제외.** 등급은 "쓰인 사실이 얼마나 최신·검증되었나"를
   말한다. 규범적 선택에는 신선도 개념이 없다. `our_choice` 는 등급에 들어가지 않되
   `provenance` 에는 **반드시** 실린다. 등급이 여럿이면 **가장 나쁜 것이 이긴다**(C > B > A).
4. **(d) 성격의 운영 임계를 `ModelConstant` 로 통합.** 신선도 임계 · 7.3의 SLA N일 ·
   4.5의 강등 임계는 전부 규범적 선택이다. 별도 설정 개념을 새로 만들지 않고
   `ModelConstant` + `our_choice` 로 등재해 **감도분석 대상**에 포함시킨다.
5. **포맷 함수 "1개"의 정의**(9.1) — 언어당 1개 + **언어 간 공용 골든 픽스처 파일**.
6. **`schwabeIndexPct` 를 시나리오별로 이동**(5.2 F-1).

### 채우지 않은 것 — 실사로 승격, 값을 지어내지 않는다

| 항목 | 왜 못 채우는가 |
|---|---|
| 타임아웃 · 성능 예산 수치 | 측정하지 않았다. 현행 4500ms가 예선 실패 원인이다 |
| 추출 성공률 합격선 · 공고문 모집단 | 대상 공고문을 아직 특정하지 않았다 |
| 신선도 임계 · SLA N일 · 4.5 강등 임계 | 변경 발생 빈도를 모른다 |
| `maintenanceFeeKRW` · `marketRisk` · `guaranteeAvailable` 의 출처 | 실거래가에 대응물이 없다 |
| 회귀 검증용 합성 프로필 세트 | 7.1이 실사용 프로필 저장을 금지한다 |
| 수집 대상(지정 출처) 목록 | 미특정 |

## 1.2 의존 방향 (아키텍처 테스트로 강제)

```
web ─┐
      ├→ api ──→ engines        engines: 순수. 아무것도 의존하지 않음
admin ┘     └──→ store
ingest ──→ store
ingest ──→ llm
api    ──→ llm      (채팅 전용)
```

**금지 규칙 — 위반 시 테스트 실패:**
- `engines` 는 `llm` 을 import 하지 않는다 ← **원칙 1(판정 경로에 AI 없음)의 기계적 강제**
- `engines` 는 `store` 를 import 하지 않는다 (데이터는 주입받는다 — 주입 경로는 5.1)
- `ingest` 는 `api` 를 import 하지 않는다
- `engines` 는 모듈 전역에 **모델 파라미터 리터럴**을 두지 않는다 (5.1)

**생성 방향 (D-11 · D-12) — 단방향이다.**

```
api  ──(OpenAPI 3.1 생성)──→ contracts/openapi.json ──(JS 상수 모듈 생성)──→ web
store ──(승인된 RuleVersion · ModelConstant 생성)────────────────────────→ web
```

생성물은 **손으로 수정하지 않는다.** 재생성해서 커밋본과 바이트 비교하는 테스트로 강제한다.
역방향(생성물을 고쳐 원본에 반영)은 금지한다 — 계약 드리프트의 발생 경로다.

# Part 2. 데이터 모델 · 계보

## 2.1 Provenance — 모든 사실에 붙는다

데이터와 모델 상수를 **같은 구조**로 다룬다. 이것이 D-5와 D-6을 하나로 묶는다.

```
Provenance
  source_kind   : statute | statistic | market | normative     ← Part 0-C의 (a)(b)(c)(d)
  source_name   : 기관·통계명
  source_ref    : URL · 고시번호 · 통계표 ID
  observed_at   : 공표·관측 기준시점
  fetched_at    : 우리가 취득한 시각
  verification  : verified | unverified | stale | our_choice
```

`our_choice` 는 `normative` 전용이다. **규범적 선택을 다른 값으로 표시하는 것을 금지한다.**

**필드 필수 여부는 `source_kind` 에 따라 다르다.** 한 구조를 쓰되 의미 없는 필드를 채우지 않는다.

| 필드 | `statute` / `statistic` / `market` | `normative` |
|---|---|---|
| `source_name` · `source_ref` | 필수 | 준거가 있으면 기재, 없으면 `null` |
| `observed_at` | 필수 (기준시점) | `null` |
| `fetched_at` | 수집 데이터는 필수, 상수는 `null` 허용 | `null` |
| `verification` | `verified` / `unverified` / `stale` | **항상 `our_choice`** |

**시각 표기** `observed_at` · `fetched_at` 은 **RFC 3339 오프셋 포함 문자열**로 저장한다.
공표 통계는 KST 기준시점이 그대로 보이도록 `+09:00` 으로 적고, UTC로 뭉개지 않는다.
(현행 `meta.generatedAt` 은 `Z` 표기 — 별개 필드이며 변경하지 않는다.)

**응답에 실릴 때**는 각 항목이 `targets` 를 갖는다 — 그 사실이 근거짓는 응답 위치의
JSON Pointer 목록(D-13). 계보가 어느 숫자에 걸리는지가 기계 판독으로 확정된다.

## 2.2 엔티티

| 엔티티 | 요점 |
|---|---|
| `Region` | 지역별 시세. Provenance 보유 |
| `PolicySource` | 공고문 원문 (텍스트 + 출처 + 취득시각) |
| `RuleDraft` | LLM 추출 결과. `pending / approved / rejected / extraction_failed` |
| `RuleSpanMapping` | 규칙 필드 ↔ 원문 구간 `(field_path, start, end)` |
| `RuleVersion` | **승인된** 규칙. 불변. `supersedes` 로 이력 연결 |
| `ModelConstant` | 모델 상수 + Provenance |
| `User` / `Role` | 3종 역할 |
| `ApprovalRecord` | 누가·언제·무엇을·왜 |
| `AuditEvent` | append-only |

## 2.3 활성 규칙 결정 (판정에 무엇이 참여하는가)

> 판정은 `RuleVersion` 중 **`approved`** 이고 `effective_from <= now < effective_to` 인 것만 사용한다.
> `RuleDraft` 는 어떤 경로로도 판정에 참여할 수 없다.

이 규칙은 **쿼리 계층에서 강제**하고 전용 테스트로 고정한다.
`RuleDraft` 가 판정에 새어드는지 검사하는 테스트를 반드시 둔다 — 원칙 2의 기계적 강제.

**프로세스 수명 캐시를 금지한다.** 현행 `engines/__init__.py` 는 `load_regions` · `load_policies` 를
`lru_cache(maxsize=1)` 로 감싸 프로세스가 사는 동안 다시 읽지 않는다. 이 상태로 저장소를 붙이면
**배치가 갱신해도, 규칙관리자가 승인해도 재기동 전까지 판정에 반영되지 않는다.**
D-2와 정면으로 충돌하고, **핵심 시연 장면(승인 → 시민 화면 변화)이 그 자리에서 무너진다.**

- 요건: **승인·배치 반영이 재기동 없이 보여야 한다.** 이것을 테스트로 고정한다 —
  저장소를 갱신하고 재기동 없이 판정을 다시 호출해 결과가 바뀌는지 확인한다.
- 캐시를 두려면 **저장소 갱신에 연동된 무효화**가 있어야 한다. 없으면 캐시를 두지 않는다.

## 2.4 데이터 등급 (D-5)

판정 응답에 `dataGrade` 를 싣는다. **거부하지 않는다.**

| 등급 | 조건 |
|---|---|
| `A` | 입력 전부 `verified` 이며 신선도 기준 이내 |
| `B` | 일부 `stale`, **또는 해당 정책에 검토 대기 중인 변경이 있음(`pending_review`)** |
| `C` | `unverified` 포함 |

**산정 규칙 (D-13 · Part 0-E)**

- **산정 대상** 이 판정에 실제로 쓰인 사실의 Provenance 중 `verification != our_choice` 인 것.
  규범적 선택은 신선도 개념이 없으므로 등급에 들어가지 않는다. `provenance` 에는 실린다.
- **우선순위** 여러 조건이 동시에 걸리면 **가장 나쁜 등급이 이긴다** (`C` > `B` > `A`).
- **사유 반환** 등급과 함께 사유 목록을 반환한다. 각 사유는 **원인 유형을 구분**해 담는다 —
  `stale`(신선도) · `unverified`(검증) · `pending_review`(승인 적체).
  대응 주체가 다르기 때문이다(배치 vs 규칙관리자). 한 등급 글자로 뭉치면 구분이 사라진다.
- 각 사유는 해당 사실의 `provenance` 항목을 가리킨다.

> **신선도 임계는 미정이다.** 며칠부터 `stale` 인지 정하려면 변경 발생 빈도를 알아야 한다.
> 임계는 (d) 규범적 선택이므로 `ModelConstant` + `our_choice` 로 등재한다(Part 0-E).
> **값을 감으로 정해 코드에 박는 것을 금지한다.** 실사 목록 참조.

> **`pending_review` 가 등급에 반영되는 이유 (중요).**
> 승인 게이트는 방치되면 오히려 데이터를 낡게 만든다. 대기 큐에 규칙이 쌓인 채
> 아무도 보지 않으면 시민은 낡은 정책으로 판정받는다.
> 이를 숨기지 않고 **"이 정책은 최근 공고 변경이 검토 대기 중입니다"** 로 노출하면
> 방치가 시스템 안에서 드러난다. 7.3의 SLA와 함께 동작한다.

## 3.1 필드별 도출 가능성 — **실거래가로 전부 채워지지 않는다**

`Region` 이 판정에 넘기는 필드는 8개다. 그중 셋은 **실거래가 원자료에 대응물이 없다.**
이것을 확인하지 않고 "실데이터 연동"이라고 말하면 그 셋은 조용히 예시값으로 남는다.

| 필드 | 실거래가에서 도출 | 처리 |
|---|---|---|
| `jeonseMedianKRW` · `monthlyDepositKRW` · `monthlyRentKRW` | 가능 (집계) | 집계 단위 확정 필요 — 아래 |
| ~~`jeonseRatioPct`~~ · `conversionRatePct` | **아래 정정 참조** / 가능 (파생 계산) | 산식을 문서로 남긴다 |

> **⚠️ 정정 (2026-08-14) — `jeonseRatioPct` 는 전월세 API 만으로는 도출 불가다.**
>
> 전세가율 = **전세보증금 / 매매가** 인데, 국토교통부 실거래가의 **전월세** 엔드포인트에는
> 매매가가 없다. 매매 엔드포인트(`getRTMSDataSvcAptTradeDev`)를 **따로** 불러야 성립하며,
> 그것은 별도 활용신청 대상일 수 있어 **수집 범위 확대**에 해당한다.
> W-market 이 3단계 착수 전 확인에서 보고했고 코디네이터가 확인했다.
>
> **3단계에서의 처리:** 값을 갱신하지 않고 이전 값을 유지하되, 계보에서 **출처 미특정**으로
> 드러낸다. 다른 필드가 실측으로 채워질 때 이 필드만 예시값으로 남는다는 사실이 숨으면 안 된다.
>
> **대용값을 만들지 않는다.** 보증금/중앙값 같은 근사를 넣으면 그 순간 (d)를 (c)인 척하는
> 것이 되고, 이 값은 `risk` 엔진의 전세가율 가중치를 **직접** 움직인다 (Part 0-C 지배 규율).
>
> **✅ 재정정 (2026-08-14, 사용자 승인) — 매매 API 를 수집 대상에 넣는다.**
> 따라서 `jeonseRatioPct` 는 **도출 가능**해지고 예시값으로 남기지 않는다.
>
> 다만 **무엇을 계산하는지 정확히 적는다.** 전세가율에는 두 가지 계산이 있고 값이 다르다 —
> `median(전세) / median(매매)` (중앙값의 비) 와 `median(전세ᵢ / 매매ᵢ)` (비의 중앙값).
> 실거래가는 전월세와 매매가 **같은 물건으로 짝지어지지 않으므로**(거래된 물건이 다르다)
> 후자는 계산할 수 없다. 우리가 내는 값은 **중앙값의 비**이며, 산식 문서와 계보에 그렇게 적는다.
>
> 집계 조건(아파트 · 85㎡ 이하 · 최근 3개월 · 같은 시군구)은 **전세와 매매에 동일하게** 건다.
> 한쪽만 조건이 다르면 비율이 조건 차이를 재게 된다.
> 매매 표본이 최소 건수 미달이면 **갱신하지 않는다** — 모자란 표본으로 계산해 내놓지 않는다.
>
> 한국부동산원 공표 전세가율과 값이 다를 수 있다(모집단·산출 방식이 다르다).
> **우리 값을 그쪽 공표값인 척하지 않는다.**
>
> `conversionRatePct` 는 도출 가능하다. 산식은 한국부동산원 통계산출항목에서 원문확인했다 —
> **전월세전환율(%) = 월세 × 12 / (전세가격 − 월세보증금) × 100.**

> ### ✅ 3차 정정 (2026-08-15, 사용자 승인) — **짝지을 수 있다. 두 비율을 「비의 중앙값」으로 낸다**
>
> 위 재정정이 「실거래가는 전월세와 매매가 **같은 물건으로 짝지어지지 않으므로** 후자는
> 계산할 수 없다」고 적었다. **그 서술을 정정한다.** 거래 건을 1:1 로 짝지을 수 없는 것은
> 맞지만, **집계 단위를 셀로 두면 짝이 성립한다.**
>
> **셀 = 법정동(`umdNm`) + 단지명(`aptNm`) + 전용면적 구간.** 셀 안에서 각 통계의 중앙값을
> 먼저 구하고, 셀 단위 비를 만든 뒤, **셀들의 비에 중앙값**을 취한다. 거래를 데카르트 곱으로
> 짝지으면 거래가 많은 셀이 중앙값을 지배하므로 그렇게 하지 않는다.
>
> #### 왜 바꾸는가 — 실측 (`diligence/FINDINGS-6.md` · 지역 10건 · API 60호출 · 원시 23,677건)
>
> | | 현행 (중앙값의 비) | 짝지음 (비의 중앙값) |
> |---|---|---|
> | 전월세전환율 · 공표값 대비 평균절대오차 | **2.30%p** | **0.14%p** |
> | 전세가율 · 공표값 대비 평균절대오차 | **7.65%p** | **2.44%p** |
> | `risk` 가중치 밴드가 공표값과 일치 | **5/10** | **8/10** |
>
> **전월세전환율은 10/10 지역에서 현행이 더 낮다. 예외가 없다.** 현행이 어긋난 5개 지역 중
> **4개가 관대한 쪽**이며(순합 −30) 이는 **불변조건 7에 정면으로 걸린다.**
>
> **모집단 쪽 근거도 원문확인됐다.** 한국부동산원 전국주택가격동향조사(승인번호 304004)는
> **단지(PSU) → 개별 호(SSU)** 로 층화 2단계 추출한 **같은 표본주택**에 대해 매매가격 ·
> 전세가격 · 월세가격을 모두 산정한다. 짝짓는 절차가 따로 있는 것이 아니라 **표본 설계 자체가
> 짝을 만든다.** 우리가 셀로 짝짓는 것은 그 구조를 실거래가 자료에서 흉내 내는 것이다.
>
> **면적구간 정의가 결과를 만들지 않는다.** 구간 폭을 1㎡ ↔ 5㎡ 로 바꿨을 때 값의 최대 이동은
> 0.12%p(전환율) · 0.46%p(전세가율)였다.
>
> #### 그래도 확인되지 않은 것 — 값을 지어내지 않는다
>
> **한국부동산원이 「비의 중앙값」을 쓰는지 「중앙값의 비」를 쓰는지는 원문에서 확정하지
> 못했다.** 통계설명자료 · 이용자용 통계정보보고서(30쪽) · 조사개요 · 용어해설 · KOSIS 주석
> 다섯 곳을 전부 열었고 **산식이 어디에도 없다** (접근실패 6건, `FINDINGS-6.md` E절).
>
> **우리 값이 공표값과 가까워진 것은 강한 정황이지 원문확인이 아니다.** 그러므로
> **우리 값을 한국부동산원 공표값인 척하지 않는다** — 이 규율은 위 재정정에서 그대로 유지된다.
> 계보에 「우리 산출 · 비의 중앙값 · 셀 = 법정동+단지명+면적구간」을 적는다.
>
> #### 산식 인용의 정정
>
> `CONVERSION_FORMULA_REF` 가 가리키는 페이지는 **「오피스텔 가격동향조사」** 것이다
> (본문이 다섯 번 오피스텔이라고 말한다). 산식 자체는 우리 구현과 일치하지만 **인용이 어긋나
> 있었다.** 실사가 **아파트 쪽의 같은 성격 페이지를 찾지 못했다.** 없는 URL 을 지어내지 않는다 —
> 가리키는 것이 무엇인지 그대로 적고 「아파트 대응 페이지 미확인」을 계보에 남긴다.
>
> #### 표본 문턱 — 새 상수를 만들지 않는다
>
> 짝이 성립한 **셀 수**에 기존 `ingest.market_min_sample_count` 를 건다. 미달이면
> **갱신하지 않는다**(이전 값 유지). 준거 없는 문턱을 새로 만들면 감도분석에서 다른 (d) 와
> 같은 무게를 갖게 된다. 실측 짝짓기 성립률은 **19.9% ~ 93.1%** 였고, 대전 유성구(30200)의
> 월세가 19.9% 로 가장 낮은데 **그곳이 현행 값이 가장 크게 틀리는 지역과 같다.**
>
> #### 새 상수 1건
>
> `ingest.market_pair_area_band_sqm` — 셀을 만드는 전용면적 구간 폭. **(d) 규범적 선택**이며
> `our_choice` 로 등재한다. 근거는 위 민감도 실측이다 — 1㎡ ↔ 5㎡ 에서 결과가 사실상 움직이지
> 않으므로 어느 값을 골라도 되지만, **고른다는 사실 자체가 우리 선택**이다.
| `maintenanceFeeKRW` | **불가** | 별도 출처 필요 |
| `marketRisk` | **불가** (원자료에 없는 판단값) | 통계에서 유도하거나 (d)로 명시 |
| `guaranteeAvailable` | **불가** (보증기관 상품 조건) | 별도 출처 필요 |

**규칙: 출처가 특정되지 않은 필드는 `unverified` 로 등재하고, 그 사실이 `provenance` 와
`dataGrade` 사유에 그대로 드러나게 한다.** 예시값을 실데이터인 척 두는 것을 금지한다.

## 4.2 추출 규칙 — LLM에 거는 제약

**추정 금지.** 원문에 없는 값은 `null` + `not_found` 로 표기한다.
그럴듯한 값을 채워 넣는 것이 이 단계의 지배적 실패 양상이므로,
**프롬프트와 스키마 양쪽에서** 강제한다.

**span 검증이 핵심 방어다.** LLM이 "만 19~34세"라는 규칙을 냈다면 그 근거가 된 원문 구간을 함께 내야 하고,
그 구간이 원문에 문자열로 실재하는지 **기계가 확인**한다. 실재하지 않으면 추출 실패로 처리한다.
이것이 "LLM 출력은 검증 가능하다"는 Part 0-B 주장의 구체적 실현이다.

**부분 저장 금지.** 스키마 불일치·검증 실패 시 draft를 만들지 않고 `extraction_failed` 로 기록한다.

### 4.2.1 span 의 정의 (모호하면 이 방어가 무력해진다)

`RuleSpanMapping` 의 `(field_path, start, end)` 를 다음으로 고정한다.

| 항목 | 확정 |
|---|---|
| 대상 텍스트 | `PolicySource` 에 저장된 **NFC 정규화된 추출 텍스트** (원본 파일 아님) |
| 오프셋 단위 | **유니코드 코드포인트.** 바이트·UTF-16 코드유닛 아님 |
| 구간 | `[start, end)` — 반열린 |
| `field_path` | **JSON Pointer** (RFC 6901). `RuleDraft` 루트 기준 |
| 검증 | `text[start:end]` 이 LLM이 낸 인용 문자열과 **정확히 일치**해야 한다 |

**정규화는 저장 시 한 번만 한다.** 검증 시점에 추가 정규화(공백 접기 · 전각/반각 변환 ·
줄바꿈 제거)를 하지 않는다. 검증기가 문자열을 주무르기 시작하면 무엇이든 통과시킬 수 있고,
그 순간 4.2의 "핵심 방어"가 사라진다. 원문 쪽 표기 흔들림은 **저장 시 정규화**로만 흡수한다.

### 4.2.2 실패 단위 · 재시도

- **실패 단위는 draft 전체다.** span 하나가 검증에 실패하면 그 draft는 `extraction_failed` 다.
  필드 단위 부분 저장은 "부분 저장 금지"와 직접 충돌한다.
- **`null` + `not_found` 는 실패가 아니다.** 원문에 없다는 것을 정직하게 보고한 것이므로
  span이 없어야 정상이다. 이 경우에만 필드가 비어 있을 수 있다.
- **재시도는 정해진 횟수까지.** 소진되면 `extraction_failed` 로 기록하고 사람 큐로 올린다.
  실패는 숨기지 않는다 — 7.2의 **추출 스키마 실패율**이 이것을 센다.

> ### ✅ 확정 (2026-08-14, 사용자 결정) — **성공률 합격선을 두지 않는다**
>
> 재시도 횟수는 결정 #19 로 `extraction.max_attempts = 2` 가 등재됐다.
> **합격선은 두지 않기로 확정한다.** 대신 7.2 의 **추출 스키마 실패율을 상시 노출**한다.
>
> **왜.** 실측 모집단이 제도 문서 **7건**이다. 7건에서 뽑은 비율에 문턱을 걸면
> 한 건이 뒤집힐 때 판정이 통째로 바뀐다 — 그것은 측정이 아니라 잡음이다.
> 이 절이 원래 적은 문장(「감으로 정한 임계는 검증했다는 착각만 만든다」)이
> 표본이 작을 때에도 그대로 성립한다.
>
> **무엇을 잃지 않는가.** 실패는 여전히 숨겨지지 않는다 — `extraction_failed` 로
> 기록되고 사람 큐로 올라가며(4.2.2) 실패율이 상태 화면에 상시 노출된다(7.2 · 7.3).
> 합격선이 하는 일은 「몇 %면 괜찮다」를 선언하는 것뿐이고, 그 선언을 뒷받침할
> 준거가 우리에게 없다.
>
> **되돌리는 조건.** 수집 대상이 늘어 표본이 의미 있는 크기가 되면 그때 다시 본다.
> 그때도 값은 (d) 규범적 선택이므로 `ModelConstant` + `our_choice` 로 등재한다.

### 4.2.3 `RuleDraft` 스키마

- **형식** JSON Schema 2020-12, `additionalProperties: false`. `contracts/` 에 두고
  D-12와 같은 재생성 diff 장치를 건다.
- **판정에 실제로 쓰이는 필드만** 정의한다. 현행 `policies.json` 의 `criteria` 는
  `ageMin` · `annualIncomeMaxKRW` · `requireSME` · `regionPrefixes` 같은 고정 필드 집합이다.
  **일반적 규칙 표현 언어를 새로 만들지 않는다** — 쓰지 않는 표현력은 검증 불가능한 표면만 늘린다.
- 스키마 확장이 필요하면 8.2 절차를 따른다. 필드가 늘면 `eligibility` 엔진도 같이 바뀐다.

## 4.3 변경 유형 — 게이트는 유지하되 비용을 차등한다

정책 변경은 한 종류가 아니다. 셋을 같은 절차에 태우면 담당자가 견디지 못하고,
견디지 못하면 승인이 밀리고, 밀리면 데이터가 낡는다.

| 유형 | 성격 | 검토 요건 |
|---|---|---|
| **① 신규 제도 신설** | 규칙 전체를 새로 생성 | **전체 검토** — 4.4의 모든 항목 |
| **② 요건 변경** | 기존 규칙의 일부 필드 변경 | **diff 검토** — 변경 필드만 + 영향 사례 |
| **③ 수치 갱신** | 구조 동일, 금리·한도 숫자만 변경 | **경량 검토** — 4.5 |

**자동 승인은 도입하지 않는다.** 원칙 2를 약화시키지 않는다.
금리 숫자 하나가 틀리면 그 정책을 매칭받는 **모든 사용자의 판정이 전부 틀린다**
(Part 0-B: B유형의 실패 반경은 "전원").

> **게이트를 약화시키는 대신 게이트를 싸게 만든다.** 이것이 이 절의 설계 의도다.

## 4.4 검토 화면 요건 — ①② (D-3 원칙 3의 실현)

승인이 거수기가 되지 않으려면 검토자에게 **판단 근거**가 있어야 한다. 다음은 필수다.

1. 추출된 규칙 각 필드 옆에 **근거 원문 구간을 대조 표시**
2. 승인 시 **기존 판정이 어떻게 바뀌는지**를 실제 사례로 제시 (회귀 결과)
3. ②의 경우 **변경 전/후 diff**를 필드 단위로 표시
4. 반려 시 사유 입력 필수

## 4.5 경량 검토 요건 — ③ (30초 안에 끝나야 한다)

수치 갱신은 다음 넷만 보이면 승인 판단에 충분하다. 그 이상을 요구하지 않는다.

1. **바뀐 숫자** (전 → 후)
2. **근거 원문 구간**
3. **변경폭** (절대·상대)
4. **판정 영향** — 이 변경으로 결과가 달라지는 사례 수

동일 유형 다건은 **일괄 승인**을 허용한다. 단 일괄 승인도 건별 `ApprovalRecord` 를 남긴다.

**임계 초과 시 강등:** 변경폭이 사전 정의한 임계를 넘으면 ③이라도 ② 절차로 올린다.
수치만 바뀌었더라도 폭이 크면 그것은 정책 변경이다.

## 4.6 동시성 — 승인은 한 번만 일어나야 한다

승인은 판정을 바꾸는 유일한 경로다. 여기서 경합이 나면 감사추적이 사실과 어긋난다.

- **같은 draft를 두 사람이 승인하는 것을 막는다.** 승인은 `pending` 상태를 조건으로 하는
  단일 전이여야 하고, 두 번째 시도는 **실패**해야 한다. 두 개의 `RuleVersion` 이 생기지 않는다.
- **일괄 승인은 원자적이다.** 한 건이라도 실패하면 전체가 반영되지 않는다.
  단 `ApprovalRecord` 는 4.5대로 **건별**로 남는다 — 원자성은 반영에 걸리고 기록에는 걸리지 않는다.
- **배치와 승인은 동시에 돈다.** 배치가 새 draft를 만드는 동안 승인이 진행될 수 있다.
  배치는 **승인된 `RuleVersion` 을 건드리지 않는다.** 배치가 만드는 것은 `pending` 뿐이다.
- 위 셋을 각각 테스트로 고정한다. 동시 실행을 흉내 내 **두 번째가 거부되는 것**을 확인한다.

# Part 5. 판정 엔진 재설계

## 5.1 상수 외부화

- 모든 모델 상수를 `ModelConstant` 로 이동한다. **코드에 숫자 리터럴 금지.**
- 각 상수는 Provenance 를 보유한다 (Part 0-C 분류표가 작업 지시서다).
- **(a)** `NET_INCOME_FROM_ANNUAL` → 상수 삭제, 법정 산식 함수로 대체
- **(c)** 할인율과 기회비용률을 **분리**한다. 같은 값일 근거가 없다. 각각 출처·기준일을 갖는다
- **(d)** 감도분석 산출물을 문서와 테스트로 남긴다
- **(a)** `JEONSE_LTV` 는 전역 상수를 삭제하고 **정책 데이터 필드**로 옮긴다.
  이 필드가 없는 기존 정책은 **판정에서 해당 상품을 제외**한다. 전역 기본값으로 메우지 않는다 —
  상품마다 다른 값을 하나로 뭉개는 것이 애초의 결함이다.

### 5.1.1 주입 경로 (1.2의 "데이터는 주입받는다"의 구체형)

- 엔진 함수는 **상수 매핑을 명시적 인자로 받는다.** 모듈 전역 읽기를 없앤다.
  네 엔진이 각자 다른 방식을 발명하지 않도록 **하나의 방식만** 쓴다.
- 8.1의 "기존 필드명 변경 금지"는 **HTTP 응답 계약**에 걸리는 규칙이다.
  **파이썬 함수 시그니처는 대상이 아니다.** 엔진 시그니처는 바꿔도 된다.
- **조회 실패 시 기본값을 쓰지 않는다.** 필수 상수 전수 존재를 **기동 시** 검증하고,
  하나라도 없으면 **기동을 거부**한다(fail-closed). 런타임에 기본값이 끼어들면
  "리터럴 금지"는 이름만 남는다. 부팅 스모크(9.1)가 이 검증을 통과한 상태를 확인한다.

### 5.1.2 "숫자 리터럴 금지"의 경계

경계를 정하지 않으면 검사가 만들어지지 않거나, 만들어져도 전부 통과시킨다.

| 대상 (금지) | 비대상 (허용) |
|---|---|
| 판정 결과의 숫자를 바꾸는 값 — 요율 · 비율 상한 · 임계 · 구간 경계 · **리스크 점수 가중치** · 기간 | 단위·구조 상수 — `floor_to` 의 만원 단위, 연→월 환산의 12 |
| 운영 임계 (신선도 · SLA · 강등 폭) — (d)로 등재 | 입력 검증 상한 (`ge=` · `le=`) — 계약 파일 소관 |
| | `0` · `1` · `100` 같은 항등·백분율 환산 |

- **검사 방법** `engines/` 하위 모듈을 AST로 훑어 숫자 리터럴을 찾고,
  테스트 파일에 명시한 **허용 목록에 없으면 실패**시킨다. 허용 목록에 항목을 추가하려면
  그 줄에 근거를 적는다. 목록이 커지는 것이 곧 규율이 무너지는 신호다.

### 5.1.3 감도분석의 산출물과 합격선

**합격선은 "뒤집히지 않는다"가 아니다. "어디서 뒤집히는지 드러낸다"이다.**
감도분석의 목적은 통과가 아니라 노출이다 (Part 0-C의 SR 11-7 인용과 같은 취지).

- 산출물: **(d) 상수 × 교란폭 × 판정이 달라진 사례 비율** 표.
- 교란폭은 최소 두 개(작은 폭 · 큰 폭)를 쓰고, **그 선택 자체가 (d)임을 문서에 밝힌다.**
- 대상 사례는 7.1이 실사용 프로필 저장을 금지하므로 **합성 프로필 세트**를 쓴다(9.2 참조).
- 테스트는 표가 **생성되는지**를 고정한다. 특정 수치를 통과 조건으로 걸지 않는다.

### 5.1.4 프론트엔드 생성물

D-11에 따라 `web` 의 판정 사본이 쓰는 상수·정책 규칙은 이 저장소에서 생성된다.
**5.1은 프론트 생성물에도 그대로 적용된다** — 생성원이 같기 때문에 자동으로 성립한다.
`frontend/app.js` 안에 남아 있는 자체 상수(연소득 5천만 · 30% 상한 등)는 이때 제거된다.

## 5.2 확정된 결함 수정

- **F-1** 슈바베지수를 재정의한다. 권장액이 아니라 **검토 중인 실제 시나리오의 주거비/소득**.
  현재 구현은 상수를 되돌려주는 항등식이다.
- **F-2** 권장액 상한을 **정당화 가능한 단일 규칙**으로 통합한다.

### 5.2.1 F-1 — 어느 시나리오인가 (계약 변경, 8.2 절차 대상)

`analyze()` 는 시나리오 **배열**을 돌려준다. "실제 시나리오"를 특정하지 않으면 구현이 갈린다.

- **슈바베지수는 시나리오별 값이다.** `scenarios[]` 각 항목에 싣는다. 최상위 단일값을 두지 않는다.
  측정 대상이 시나리오마다 다르므로 하나를 고르는 것은 임의 선택이다.
- `affordability.schwabeIndexPct` 는 **제거**한다. 그 자리에 권장액의 소득 대비 비율이 필요하면
  **측정값이 아님이 드러나는 이름**을 쓴다. 상한을 지수처럼 보이게 하는 것이 F-1의 본질이다.
- **불변식이 바뀐다.** 측정값이 되는 순간 `<= 100` 은 성립하지 않는다 —
  주거비가 소득을 넘는 시나리오가 실재하기 때문이다. 5.3에서 상한을 뗀다.
- **영향받는 소비자** `frontend/app.js` 의 게이지(`gaugeSVG(a.schwabeIndexPct, a.band)`)는
  0~100 척도를 전제한다. 상한 없는 값을 그대로 넣으면 눈금이 깨진다. 표시 방식을 함께 바꾼다.
- 이것은 응답 계약 변경이다. **8.2 절차로 처리한다** — 계약 파일 · 서버 · 프론트 생성물이
  같이 바뀌고, 양쪽 테스트가 동시에 깨져야 한다.

### 5.2.2 F-2 — "정당화 가능"의 판정 방법

정당화 여부를 사람의 인상으로 판정하지 않는다. 통합된 단일 규칙은 다음을 **문서로 갖춰야** 한다.

1. 어떤 준거에서 나왔는지 — 없으면 **없다고 적는다**(`normative` · `our_choice`)
2. 두 상수 중 무엇을 버렸고 그 결과 판정이 어떻게 달라지는지 — 회귀 사례 수
3. 감도분석 표에서의 위치 (5.1.3)

셋이 갖춰지지 않은 통합안은 반려한다. **판정자는 코디네이터다.**

## 5.3 불변식 (테스트로 강제)

```
npv5y <= tco5y
0 <= scenarios[].schwabeIndexPct          ← 상한 없음 (5.2.1)
0 <= fitScore <= 100
recommended <= max
동일 입력 → 동일 출력 (바이트 단위, 시각 의존 필드 제외)
engines 는 llm 을 import 하지 않는다
engines 는 모델 파라미터 리터럴을 갖지 않는다
RuleDraft 는 판정에 참여하지 않는다
```

**"바이트 단위"의 비교 대상 (Part 0-E)**

- `meta.generatedAt` 은 호출 시각이므로 **그대로는 절대 성립할 수 없다.**
  엔진은 시계를 직접 읽지 않고 **클럭을 주입받는다**. 결정성 테스트는 클럭을 고정하고
  **응답 전체를 바이트 비교**한다. 필드를 빼고 비교하지 않는다 — 제외 목록은 자라기 때문이다.
- `rationale` 문자열은 **계약이 아니다.** 상수값을 문장에 직접 박고 있어(예: "주거비 상한을
  30%로 설정했습니다") 5.1이 끝나면 전부 바뀐다. 골든 스냅샷(9.2 #4)은 **숫자·상태 필드**를
  대상으로 하고, `rationale` 은 **별도 스냅샷**으로 분리해 상수 변경 시 의도적으로 갱신한다.
  섞어 두면 상수 하나 바꿀 때마다 회귀 테스트가 통째로 흔들려 아무것도 잡지 못한다.

화면에서 버튼을 숨기는 것으로 대신하지 않는다.
**거부 케이스를 테스트로 고정**한다 — 상담원 **세션**으로 승인 API를 호출하면 반드시 거부되어야 한다.

**"내부 정보"가 실리는 방식 (Part 0-E).** `/api/analyze` 는 역할에 따라 스키마가 갈리지 않는다.
내부 정보는 **인증된 요청에만 채워지는 부가 필드**로 같은 응답에 실리고, 계약 파일에
`x-requires-role` 로 표기한다. 별도 엔드포인트로 나누면 같은 판정을 두 번 계산하게 되고
둘이 어긋날 수 있다. **익명 응답에 해당 필드가 없음**을 권한 테스트로 고정한다.

## 6.2 프론트엔드 방침

- **판정 화면** — 기존 바닐라 유지. **오프라인 동작 보존**(빌드툴·CDN 금지). 상담원 확장은 조건부 렌더.
- **규칙 관리 화면** — 별개. 오프라인 동작 요구 대상이 아니므로 빌드 도구 사용을 허용한다.
  단 로컬에서 네트워크 없이 기동되어야 한다(사전 빌드 산출물 동봉).

**"오프라인 동작 보존"의 정의 (D-11).** 이 문구가 가리키는 것은 `frontend/app.js` 의
로컬 판정 경로다. 다음 셋을 모두 뜻한다.

1. **런타임 외부 의존 금지** — CDN · 빌드 산출물 다운로드 · 폰트 원격 로드 없음
2. **백엔드 없이도 화면이 뜬다** — 단, 판정 숫자는 **생성물이 있을 때만** 나온다(D-11)
3. **침묵 폴백 금지** — 백엔드 응답이 없어 로컬 경로로 내려갔다면 화면에 **명시**한다

`web` 이 소비하는 계약 상수·판정 상수·정책 규칙은 전부 생성물이다. 손으로 쓴 값이 남아 있으면
1.2의 생성물 diff 테스트가 실패한다.

**`admin` 의 사전 빌드 산출물** — 빌드 결과를 **git에 커밋**한다. 시연 노트북에서
`npm install` 이 도는 경로를 만들지 않는다(D-8: 네트워크 의존 금지).
`scripts/dev.bat` 은 커밋된 산출물을 정적 파일로 서빙만 한다. 빌드하지 않는다.

**동일 오리진.** `web` · `admin` · `api` 를 같은 오리진에서 서빙한다. 현행
`allow_origins=["*"]` · `allow_credentials=False` 는 쿠키 세션과 양립할 수 없으므로 **폐기**한다.

## 6.3 인증

로컬 실행 전제이므로 **서버 세션 기반**으로 통일한다. 6.1의 "토큰"도 같은 것을 가리킨다.

| 항목 | 확정 | 근거 |
|---|---|---|
| 자격증명 저장 | **Argon2id** (`argon2-cffi`). 평문·단순 해시 금지 | OWASP Password Storage CS |

## 6.4 상담원 → 규칙관리자 이상 신고 경로

**상담원은 이 시스템에서 가장 자주 쓰는 사용자이자, 데이터 오류의 최전선 탐지자다.**
고객 앞에서 *"그 제도 지난달에 없어졌는데요"* 를 듣는 사람은 상담원이지 규칙관리자가 아니다.

이 피드백 경로가 없으면 현장에서 발견된 오류가 시스템에 들어오지 못한다.

- 판정 화면(상담원 모드)에서 **정책·시세 항목별로 「이상 신고」** 를 올릴 수 있다
- 신고는 규칙관리자의 대기 큐에 **별도 유형**으로 쌓인다 (추출 draft와 구분)
- 신고자·시각·대상·사유를 `AuditEvent` 로 남긴다
- **상담원은 여전히 규칙을 바꿀 수 없다** — 신고는 제안이지 변경이 아니다. SoD 유지

부수 효과: 이 경로가 **7.3의 간헐 업무를 깨우는 자연스러운 트리거**가 된다.
배치가 감지하지 못한 변경을 사람이 먼저 발견하는 경우가 실제로 더 많을 수 있다.

**신고와 추출 draft의 충돌 처리 (잠정):**
같은 정책에 대해 배치가 만든 draft와 상담원 신고가 동시에 큐에 있을 수 있다.

- 대상 정책이 같으면 **하나의 검토 항목으로 병합**하고, 신고를 draft의 **컨텍스트로 첨부**한다.
  검토자는 "기계가 이렇게 추출했고, 현장에서는 이런 문제가 보고됐다"를 함께 본다.
- 신고만 있고 draft가 없으면(배치가 감지 못 한 경우) **신고 단독 항목**으로 큐에 남는다.
  이 경우 규칙관리자가 수동 입력하거나 재추출을 지시한다.
- 병합해도 **신고와 draft의 `AuditEvent` 는 각각 독립적으로 보존**한다.

> 잠정 규칙이다. 실제 운영에서 신고 빈도와 draft 빈도의 비율을 본 뒤 재검토한다.

# Part 7. 감사추적 · 관측성

## 7.1 AuditEvent (append-only · 수정/삭제 금지)

`actor · at · action · target · outcome · before/after`

**필수 기록:** 규칙 승인·반려 / 로그인 및 실패 / 배치 실행 결과 / 권한 거부

**개인정보:** 시민의 판정 요청 **프로필은 저장하지 않는다.** 요청 메타(시각·등급·규칙버전)만 남긴다.

**append-only 의 강제 수단 (규율이 아니라 구조로).** 두 겹으로 건다.

1. `store` 인터페이스가 `AuditEvent` 에 대해 update·delete를 **노출하지 않는다**
2. SQLite에 `BEFORE UPDATE` · `BEFORE DELETE` 트리거를 두어 `RAISE(ABORT)` 시킨다

저장소를 교체해도 같은 보장이 유지되어야 한다(부록 A). 두 겹이 실제로 막는지를 테스트로 고정한다 —
저장소 계층에서 직접 수정·삭제를 시도해 **실패하는 것**을 확인한다.

**개인정보 금지의 적용 범위 — 저장소만이 아니다.**

| 경로 | 규칙 |
|---|---|
| `AuditEvent` · 저장소 | 프로필 저장 금지 (위) |
| **파일 로그**(7.2) | 요청 본문을 찍지 않는다. 오류 로그도 예외가 아니다 |
| **6.4 이상 신고 사유** | 자유 입력이므로 고객 상황이 섞일 수 있다. 화면에 **고객 개인정보를 적지 말라고 명시**하고, 신고 대상은 정책·시세 **항목**으로 한정한다 |
| **LLM 채팅**(#1) | 프로바이더로 나가는 내용은 로컬에 남기지 않는다 |

> **`AuditEvent` 보존 기간은 미정이다.** 로컬 시연에서는 삭제할 이유가 없어 무기한이나,
> 배포 시에는 정책이 필요하다. 부록 A의 "배포 시 추가로 필요한 것" 목록에 넣는다.

## 7.2 관측 지표

배치 성공률 · 데이터 신선도 · LLM 호출 성공률과 지연 · **추출 스키마 실패율** · 승인 대기 건수.

로컬 실행이므로 외부 APM을 도입하지 않는다. 파일 로그 + 상태 화면으로 충분하다.

## 7.3 대기 큐 SLA — 간헐 업무는 잊힌다

규칙 승인은 **월 단위 소수 건**의 간헐 업무다. 이런 업무는 담당자가 화면을 열지 않는다.
그러면 대기 큐에 규칙이 쌓인 채 방치되고, **승인 게이트가 오히려 데이터를 낡게 만드는 역설**이 생긴다.

이를 막는 장치를 둔다. **pull(담당자가 보러 오기)을 기대하지 않고 push 한다.**

| 장치 | 내용 |
|---|---|
| **SLA 정의** | draft 생성 후 N일 초과 미처리 건을 `overdue` 로 표시 |
| **알림** | 신규 draft 발생 시 · SLA 초과 시 |
| **상태 화면** | 대기 건수 · 최장 대기일 · overdue 건수를 상시 노출 |
| **시민 화면 반영** | 해당 정책 판정에 `pending_review` 표시 (2.4) |

마지막 항목이 핵심이다. **방치를 숨기지 않고 사용자에게 드러내면**, 방치가 조직 안에서
보이지 않는 상태로 지속될 수 없다. 이는 이 제품의 설계 철학(근거를 감추지 않는다)과 일치한다.

**알림 채널 — D-8 아래에서 실현 가능한 것으로 한정한다.**
로컬 단일 호스트이고 네트워크 의존이 금지되므로 **메일·메신저 push는 범위 밖**이다. 대신 셋을 둔다.

1. `admin` 진입 시 **상시 배지** — 대기 건수 · 최장 대기일 · `overdue` 건수
2. **배치 실행 결과 출력** — 신규 draft 발생과 SLA 초과를 콘솔·파일 로그에 남긴다
3. **시민 화면 반영** — `pending_review` (2.4). 이것이 사실상 가장 강한 압력이다

> 외부 채널 연동은 부록 A의 "배포 시 추가로 필요한 것" 목록으로 넘긴다.
> 로컬에서 되지 않는 것을 스펙에 적어 두면 8단계 리허설에서 구멍이 드러난다.

> **N값은 미정이다.** 변경 유형별 실제 발생 빈도를 모르면 정할 수 없다. 실사 목록 참조.
> N은 (d) 규범적 선택이므로 확정 시 `ModelConstant` + `our_choice` 로 등재한다(Part 0-E).

## 8.2 계약 관리 규칙 (Part 0-A 대응 — 반드시 지킬 것)

1. 계약은 **단일 파일**로 존재하고, 서버와 클라이언트가 **같은 파일**에서 생성·검증한다.
2. 계약 변경은 **반드시 계약 파일 변경을 동반**한다. 코드만 바꾸는 것을 금지한다.
3. 계약을 바꾸면 **양쪽 테스트가 동시에 깨져야 한다.** 한쪽만 깨지면 계약이 약한 것이다.
4. **단위와 반올림 규칙을 계약에 명시**한다 (예선의 80만/81만 사고 재발 방지).
5. 계약 변경은 **코디네이터만** 수행하고, **영향받는 모든 작업자에게 전파**한다.
   > 예선에서 발생한 유일한 계약 사고는 코디네이터가 계약을 바꾸고 **한쪽에만 통지**한 것이었다.

**계약 파일의 실체는 D-12에서 확정했다.** `contracts/openapi.json`, 코드에서 생성, 재생성 diff로 강제.

```js
// app.js:32-36
function timeoutFor(path) {
  if (path === '/api/chat')    return CHAT_TIMEOUT_MS;    // 75000
  if (path === '/api/analyze') return ANALYZE_TIMEOUT_MS; // 15000
  return FETCH_TIMEOUT_MS;                                //  4500
}
```

**4500ms 는 이미 `analyze` 에 걸린 값이 아니다.** `health` · `regions` · `meta` 세 GET 에만
걸린다. 그리고 사고 경위는 `app.js:20-27` 주석이 직접 적고 있다 —

> `/api/chat` round-trips a live LLM: measured 2.7-4.5s for a single tool call and ~10s for
> a four-tool turn... **The old single 4500ms budget aborted those calls mid-flight, and the
> chat silently fell back to the built-in template**

즉 **예선 사고의 대상은 `chat` 경로였고, 예산 분리는 예선 말미에 이미 적용되어 있다.**
Part 0-A 의 표 행에도 경로를 명시했다.

**따라서 경고를 재조준한다. 위험은 "4500 을 승격하는 것"이 아니라
"이미 분리된 예산을 다시 하나로 합치는 것"이다.** 하나로 뭉치면 `chat` 기준으로 잡혀
`analyze` 가 75초를 기다리거나, `analyze` 기준으로 잡혀 `chat` 이 다시 잘린다.
후자가 정확히 예선 사고다. **계약이 그 사고를 다시 가능하게 만드는 형태여서는 안 된다.**

**값은 측정에서 유도한다. 아래 규칙을 고정한다.**

1. 타임아웃은 **측정에서 유도한다.** 저장소 도입 후의 실측 지연 분포를 근거로 삼는다
2. **클라이언트 타임아웃 > 서버 응답 예산 + 마진.** 역전되면 정상 응답이 폴백으로 처리된다
3. 확정된 값은 **계약 파일의 `x-` 확장에만** 존재한다. 코드에 직접 쓰지 않는다
4. 서버·클라이언트가 **같은 파일에서 읽는다.** 한쪽만 바꾸는 경로를 만들지 않는다
5. **타임아웃 발생 시 동작을 계약에 함께 적는다** — 재시도 횟수, 폴백 여부, 화면 표기

6. **경로별로 나눈다.** 지연 성격이 다른 경로를 하나의 예산으로 묶지 않는다 (위 정정 참조).

### 8.3.1 실측 결과 (2026-08-13, 0단계 완료 시점)

실기동한 `uvicorn` 에 클라이언트 벽시계 기준으로 측정했다 — 루프백 HTTP 왕복 포함,
서버 내부 함수 시간이 아니다. 프론트 타임아웃과 비교되는 값이 그것이기 때문이다.
프로필 4종 × 200회. 프로바이더 `offline`. 산출물은 `backend/tests/api/artifacts/`.

| 경로 | p50 | p95 | p99 | max | 콜드 1회차 |
|---|---|---|---|---|---|
| `POST /api/analyze` | 2.8ms | 4.0ms | 5.1ms | 11.5ms | 22.5ms |
| `GET /api/health` | 0.9ms | 1.4ms | — | 1.9ms | — |
| `GET /api/regions` | 1.0ms | 1.5ms | — | 4.6ms | — |
| `GET /api/meta` | 1.4ms | 2.0ms | — | 2.5ms | — |
| `POST /api/chat` | 3.1ms | — | — | 4.2ms | — (offline 경로만) |

**`analyze` 는 15000ms 예산의 0.03% 다.** 4500ms 가 걸린 세 GET 도 p95 2.0ms 이내로
오히려 헐겁다. 원 서술이 가리킨 위험은 현재 코드에 존재하지 않는다.

### 8.3.2 확정값

| 경로 | 서버 응답 예산 | 클라이언트 타임아웃 | 재시도 |
|---|---|---|---|
| `/api/analyze` | 1,000ms | 5,000ms | 0 |
| `GET` 3종 | 500ms | 3,000ms | 0 |
| `/api/chat` | **없음** | 75,000ms | 0 |

- **서버 예산은 측정값이 아니라 약속이다.** 1,000ms 는 실측 p99 의 200배이며, 그 간극은
  의도된 것이다 — 실데이터 유입 후 정책·지역 순회가 늘어나는 것을 흡수한다.
  반대로 이 값을 넘기면 그것은 회귀다.
- **GET 3종은 4500 → 3000 으로 낮춘다.** D-8 이 로컬 단일 호스트를 못박았으므로 이 셋이
  초 단위로 늘어나면 그것은 사고이고, **헐거운 타임아웃은 사고를 숨긴다.**
- **`chat` 은 외부 의존이라 서버 예산 개념이 성립하지 않는다.** 그리고 75,000ms 는
  **측정된 값이 아니다** — 라이브 LLM 호출은 키와 비용이 필요해 측정하지 않았다.
  계약에 `measured: false` 로 표시한다. 측정하지 않은 값을 측정된 값과 같은 형태로
  넣으면 8.3 #1 이 무너진다 (Part 0-C 의 「(d)를 (a)(b)(c)인 척하지 않는다」와 같은 규율).
- **재시도 0.** `analyze` 는 결정론적이라 재시도가 같은 답을 같은 시간에 낼 뿐이고,
  `chat` 은 서버측 재시도와 이중이 된다.
- **타임아웃 시 화면에 명시한다. 침묵 폴백을 금지한다** (6.2 오프라인 정의 #3 · D-11).
- 값 옆에 **측정 근거**(표본수 · 분위수 · 측정일 · 환경 · 스크립트 경로)를 함께 싣는다.
  벌거벗은 숫자만 남으면 왜 그 값인지 아무도 모르게 되고, 그때 감으로 고친다.

> **여전히 미정:** 배치 실행 시간 상한 · 추출 1건당 지연/비용 상한 (2·3단계에서 실측).
> **라이브 LLM 지연**은 실사 목록으로 승격한다.

## 8.4 버전 표기

`meta.engineVersion` 은 응답에 실리므로 계약의 일부다. 규칙이 없으면 아무도 올리지 않거나
각자 올린다.

| 대상 | 규칙 |
|---|---|
| `ENGINE_VERSION` | **판정 출력이 달라지면 올린다.** 상수 값 변경(1-②)도 포함된다 — 같은 입력이 다른 숫자를 내는데 버전이 같으면 골든 스냅샷의 근거가 사라진다. 계약 스키마가 바뀌면 major, 값만 바뀌면 minor |
| `RuleVersion` | 정책 단위로 **단조 증가하는 정수**. `supersedes` 로 이전 버전을 가리킨다(2.2). 의미를 담는 표기를 쓰지 않는다 — 판별 규칙(4.3)이 흔들리면 표기도 흔들린다 |
| `contracts/openapi.json` | OpenAPI `info.version`. 8.2 절차로만 변경 |

> 버전은 **응답에 실리는 것만** 규정한다. 내부 모듈 버전을 새로 만들지 않는다.

## 9.1 실패 유형별 방어 장치

### 9.1.1 "포맷 함수 1개"의 정의 — **현재 상태는 불합격이다**

먼저 사실. 두 구현은 이미 다른 문자열을 낸다.

| 입력 | 파이썬 | JS | 결과 |
|---|---|---|---|
| `pct(25.0)` | `"25%"` (`:g` 가 `.0` 을 지움) | `"25.0%"` (`toFixed(1)`) | **불일치** |
| `money(-750000)` | `"0원"` (`safe_int` 가 음수를 0으로) | `"-75만원"` | **불일치** |

`common.money()` 의 주석은 "must stay byte-for-byte consistent with `fmtKR()`"라고 규약을 적어 두었지만,
그 규약은 **`money` 에만 달려 있고 `pct` 에는 없다.** 규약이 주석으로만 존재하면 함수가 늘어날 때
따라오지 않는다. 9.1이 방어하겠다고 한 바로 그 실패 유형이 이미 발생해 있다.

**따라서 "1개"를 다음으로 정의한다 (Part 0-E).**

- **언어당 구현 1개** — 파이썬 1개, JS 1개. 언어를 넘는 공유 구현은 D-8 제약 아래 불가능하다.
- **판정 기준은 구현이 아니라 출력이다.** `contracts/` 에 **입력 → 기대 문자열** 골든 픽스처 파일을
  두고, **양쪽 테스트가 같은 파일을 읽는다.** 한쪽만 바꾸면 그쪽 테스트가 깨진다.
- 픽스처에는 **음수 · 0 · 억 경계 · 반올림 캐리 · 소수 자릿수**를 반드시 포함한다.
- 엔진·화면 어디서도 픽스처를 우회한 자체 포맷을 만들지 않는다.

### 9.1.2 스모크 테스트의 합격 판정

- **2xx만으로는 불합격이다.** 응답이 `contracts/openapi.json` 스키마와 **일치**해야 통과다
  (계약 파일 기반 자동 검증, 예: schemathesis).
- 기동 시 5.1.1의 **상수 전수 검증을 통과한 상태**여야 한다. 뜨지 않으면 그 자체가 실패다.
- 전 엔드포인트를 호출하되, 인증이 필요한 것은 **거부 케이스도 함께** 친다(9.2 #3).

### 9.1.3 `dev.bat` 실행 테스트의 형태

`scripts/dev.bat` 은 CP949 고정이 요구사항이다(예선에서 인코딩 문제로 파서가 붕괴했다).
자동 테스트는 둘로 나눈다.

1. **정적 검사** — 파일을 바이트로 읽어 **CP949로 디코딩 가능**한지, CP949에 없는 문자가
   섞이지 않았는지 확인한다. 이 검사는 배치를 실행하지 않으므로 CI에서 항상 돈다
2. **실행 검사** — 실제로 기동해 9.1.2의 스모크까지 간다. 사람이 돌리는 경로다

`ingest.bat` 도 같다. 정적 검사는 항상, 실행 검사는 외부 호출 없이 도는 범위까지(9.2 #8).

### 9.2.1 #8 "키 없이 전 기능 동작"의 범위

`ingest` 는 외부 API를, 추출은 LLM을 필수로 요구한다. "전 기능"을 문자 그대로 읽으면
달성 불가능하고, 느슨하게 읽으면 아무것도 검증하지 못한다. 다음으로 고정한다.

| 대상 | 키 없이 요구되는 동작 |
|---|---|
| 판정 · 화면 · 규칙 조회 · 승인 흐름 · 감사 | **전부 정상 동작** |
| 채팅(#1) | 폴백 동작. 판정 결과는 영향받지 않는다(원칙 1) |
| 시세 수집 | **정상 실패** — 저장소를 훼손하지 않고 이전 값 유지 + `stale` (Part 3) |
| 정책 추출의 LLM 호출 | **정상 실패** — `extraction_failed` 기록, 부분 저장 없음 |
| 정책 추출의 **후반부** | **전부 동작해야 한다** — 저장된 원문·draft 픽스처로 스키마 검증 · span 검증 · 회귀 생성 · 승인까지 |

마지막 줄이 핵심이다. **본선의 기술적 중심(4절)은 키 없이 검증 가능해야 한다.**
LLM 호출은 파이프라인의 한 단계일 뿐이라는 Part 0-B의 주장이 여기서 기계적으로 증명된다.

### 9.2.2 회귀·감도분석용 프로필 세트

7.1이 시민 프로필 저장을 금지하므로 **실사용 데이터를 쓸 수 없다.**
4.1 #5 · 4.4 #2 · 4.5 #4 · 5.1.3이 모두 요구하는 "결과가 달라지는 사례"의 모집단은
**합성 프로필 세트**다. `contracts/` 에 고정 파일로 두고 버전을 매긴다.

- 경계값 테스트(#6)의 축 — 0소득 · 초고소득 · 연령 경계 · 없는 지역 — 을 포함한다
- 세트가 바뀌면 골든 스냅샷이 바뀐다. **세트 변경은 계약 변경으로 취급**한다(8.2)

> **개수와 설계 책임자는 미정이다.** 정책 요건의 분포를 봐야 정할 수 있다.
> 임의의 개수를 정해 두고 "커버리지 확보"라고 말하지 않는다. 실사 목록 참조.

## 9.3 완료 판정 기준 (Definition of Done)

에이전트 작업 단위마다 전부 충족해야 완료로 인정한다.

1. 변경에 대응하는 테스트가 있고, **그 테스트가 변경 전에는 실패**했음을 보였는가
2. 전체 테스트를 통과했는가
3. **실제로 기동해서 손으로 호출**했는가
4. 계약을 건드렸으면 계약 파일도 바꿨는가
5. 새 상수를 추가했으면 **Provenance를 붙였는가**
6. 미검증 항목을 보고에 **명시**했는가

> **"돌려봤다"의 정의: 명령어와 그 출력을 보고에 첨부하는 것.**
> 첨부하지 않으면 미검증으로 간주한다.

**작업 종류에 따른 #1 · #3 의 대응물.** 그대로 적용되지 않는 경우가 있어 미리 고정한다.

| 작업 종류 | #1 "변경 전 실패" | #3 "기동해서 호출" |
|---|---|---|
| 기존 코드 변경 | 그대로 | 그대로 |
| **신규 모듈 생성** (`store` · `ingest` · `admin`) | 테스트를 **먼저 쓰고 실패를 보인다** (red → green) | 그대로 |
| **배치 작업** | 같음 | 배치를 **실행하고** 저장소 변화 전후를 첨부 |
| **`admin` 화면** | 같음 | 화면을 띄우고 **승인·반려를 실제로 눌러** 결과를 첨부 |
| **8단계 리허설** | 해당 없음 | 장면 재현 로그를 첨부 |

**#6 보고의 형식과 수신처.** 보고는 **코디네이터에게 터미널로 직접** 낸다(9.4).
다음 넷을 포함한다 — ① 실행한 명령과 출력 ② 통과/실패 ③ **검증하지 않은 것** ④ 남은 가정.
③이 비어 있는 보고는 반려한다. 비어 있는 경우는 사실상 없다.

## 9.4 병렬 에이전트 작업 규칙

- 한 에이전트는 **자기 소유 경로만** 수정한다.
- **계약 변경은 코디네이터만** 한다. 에이전트는 요청만 한다.
- 계약이 바뀌면 코디네이터가 **영향받는 전원에게 전파**한다.
- 작업 지시는 **orchestration 메일이 아니라 터미널로 직접 전달**한다.
  > 예선에서 팀명 변경 메일을 읽지 못한 채 완료한 사례가 있었다.
  > 워커는 지시받지 않으면 `check` 를 호출하지 않는다.

**소유 경로 배정표.** 규칙만 있고 배정이 없으면 강제되지 않는다.

| 소유자 | 경로 |
|---|---|
| `engines` | `backend/src/firsthome/engines/` · `backend/src/firsthome/common.py` |
| `api` | `backend/src/firsthome/main.py` · `config.py` |
| `store` | `backend/src/firsthome/store/` |
| `ingest` | `backend/src/firsthome/ingest/` |
| `llm` | `backend/src/firsthome/llm/` |
| `web` | `frontend/` (생성물 디렉터리 제외) |
| `admin` | `admin/` (소스 + 커밋된 빌드 산출물) |
| **코디네이터 전용** | `contracts/` · 모든 생성물 · `scripts/` · `docs/engineering/SPEC.md` |

- **테스트는 대상 코드의 소유자가 함께 소유**한다. 단 **교차 테스트**(계약 · 아키텍처 ·
  스모크 · 생성물 diff · 포맷 골든)는 코디네이터 소유다. 이것들이 깨지는 것이 곧 경계 위반 신호다.
- `backend/src/firsthome/data/` 의 시드 데이터는 0단계에 `store` 로 이관된다. 이관 후 소유자는 `store`.
- 두 소유자가 걸리는 변경은 **코디네이터가 순서를 정해 직렬로** 낸다. 동시에 열지 않는다.

## 10.1 시연 시 시간 압축을 명시한다

시연에서 *승인 → 시민 화면 변화* 는 몇 초 만에 일어난다. 그러나 **실제 운영 리듬은 월 단위**다
(규칙관리자는 간헐 업무자다 — 7.3).

이 격차를 말하지 않으면 심사위원은 실시간 시스템으로 오해하고,
*"실제로 이렇게 빨리 도나요?"* 라는 질문에 답이 궁색해진다.

> **시연 대본에 다음을 반드시 포함한다:**
> "실제로는 월 단위로 발생하는 업무이며, 여기서는 그 한 사이클을 압축해 보여드립니다."

숨기는 것보다 이 편이 강하다. **간헐 업무라는 사실 자체가 7.3(SLA·알림·`pending_review`)을
설계한 이유**이므로, 시간 압축을 밝히는 것이 오히려 설계 깊이를 드러낸다.

**실사(잔여 항목)는 0단계와 병렬로 진행한다.** **1-②** 를 막지 않도록 먼저 착수한다.

**중단 규칙.** 기간이 부족해지면 **3단계(시세)를 수동 갱신으로 축소**하고 2단계(정책 추출)를 완성한다.
정책 추출이 본선의 기술적 중심이며, 시세는 축소해도 서사가 무너지지 않는다.

# 부록 A. 배포 가능성 증명 (D-8)

실제 배포는 필수가 아니나 **가능함을 문서로 증명**한다.
- 저장소는 인터페이스 뒤에 두어 SQLite ↔ 외부 DB 교체가 코드 변경 없이 설정으로 가능함을 보인다
- 비밀·설정은 환경변수로 주입한다 (`.env` 는 로컬 편의 수단일 뿐 유일 경로가 아니다)
- 배포 시 추가로 필요한 것(HTTPS · 비밀관리 · 백업 · 모니터링)을 목록으로 명시한다

> **주의 — 첫 항목은 문서가 아니라 코드 결정이다.** "인터페이스 뒤에 둔다"는 `store` 의 설계
> 자체이며 **0단계 산출물**이다. 부록으로 미루면 0단계가 인터페이스 없이 지어지고, 그때 부록 A는
> 사후 증명이 불가능해진다. 7.1의 append-only 보장도 이 인터페이스가 지고 있다.

**배포 시 추가로 필요한 것 (현재 로컬 범위 밖 — 목록만 유지한다)**
HTTPS · 비밀관리 · 백업 · 모니터링 · **`AuditEvent` 보존 기간 정책**(7.1) ·
**외부 알림 채널**(7.3) · **외부 데이터의 저장·재배포 조건 확인**(실사 목록) ·
**6.4 신고 사유의 개인정보 대책** — 사유는 자유 입력이고 그 본문이 append-only 인
`AuditEvent` 에 남아 **사후 삭제 경로가 없다.** 7.1 이 정한 완화책(대상 한정 · 화면 문구)
바깥의 잔여이며, 배포 시 보존 기간 · 별도 보관 · 마스킹 중 무엇을 쓸지 정해야 한다
(계약 결정 #41).
