# contracts/ — 계약 파일

**소유자: 코디네이터 전용** (SPEC 9.4 소유 경로 배정표).
워커는 이 디렉터리의 어떤 파일도 수정하지 않는다. 변경이 필요하면 **요청만** 한다 (SPEC 8.2 #5).

`contracts` 는 런타임 컴포넌트가 아니다 (SPEC 1.1).

## 두 종류를 섞지 않는다

| | 손으로 쓴 계약 원본 | 코드에서 생성된 산출물 |
|---|---|---|
| 성격 | 시스템의 **입력**. 코드가 이것을 따른다 | 시스템의 **출력**. 코드에서 재생성된다 |
| 파일 | `provenance.schema.json`<br>`model_constants.json`<br>`format_golden.json`<br>**`rule_draft.schema.json`** | **`openapi.json`** — `scripts/gen_contracts.py` 가 생성. 재생성 diff 로 강제 (D-12, ✅ Wave 2)<br>**`frontend/generated/*.js`** — 같은 스크립트가 생성 (D-11, ✅ 결정 #34)<br>`profiles.synthetic.json` (9.2.2, 실사 미정) |
| 검증 | 사람이 검토. 재생성 대상 아님 | **재생성 후 바이트 비교** (SPEC 1.2 · D-12) |

> 생성물 diff 테스트가 손으로 쓴 원본까지 재생성하려 들면 0단계가 무너진다.
> 새 파일을 추가할 때 어느 칸에 속하는지 이 표에 먼저 적는다.

## 코디네이터가 8.2 절차로 내린 결정

계약 파일 안에 `$comment` 로 근거를 남긴 결정은 다음과 같다. SPEC 본문과 충돌하는 것이 아니라,
SPEC의 두 요구가 동시에 성립하도록 경계를 고정한 것이다.

1. **`observed_at` 등 필수 여부를 `verification` 에 건다** (`provenance.schema.json`).
   SPEC 2.1 표는 `statute/statistic/market` 에 `observed_at` 필수라고 적지만, D-14 는 1-① 에서
   현행 값을 `unverified` 로 등재하라고 요구한다. 출처를 모르는 것이 곧 `unverified` 의 의미이므로
   필수 조건은 `verified`/`stale` 에만 건다. 기각한 대안 — 자리표시자 날짜 기입(값 날조 금지 위반),
   `(d)` 로 분류(0-C의 분류 혼동 금지 위반).

2. **`GUARANTEE_MIN_DEPOSIT` 를 잠정 `statute` + `unverified` 로 등재** (`model_constants.json`).
   SPEC 의 "불명 시 (d) 처리"는 실사 **종료 후**의 폴백이다. 실사 진행 중에 `our_choice` 로 넣으면
   2.4에 따라 `dataGrade` 산정에서 빠져 "출처를 모른다"는 사실이 등급에서 사라진다.

3. **수치 타입은 `float` 유지** (`model_constants.json` → `injectionContract.numericType`).
   `Decimal` 전환은 반올림 경로를 바꿔 1-① 완료 기준("판정 숫자가 1-① 이전과 동일")과 충돌한다.

4. **`Z` 표기 금지, 숫자 오프셋 강제** (`provenance.schema.json`).
   SPEC 2.1 "UTC로 뭉개지 않는다"를 정규식으로 강제한 것. `meta.generatedAt` 은 별개 필드이며 영향 없다.

5. **`RuleVersion.origin` 판별자를 둔다.** (W-store 질의 2026-08-13)

   SPEC 2.2 에는 `Policy` 엔티티가 없다. 따라서 `policies.json` 시드가 들어갈 곳은
   **승인된 규칙**인 `RuleVersion` 뿐인데, 이 프로토타입 데이터는 사람이 승인한 적이 없다.
   가짜 승인자를 넣는 것은 SPEC 7.1 이 지키려는 감사추적을 그 자리에서 날조하는 것이다.

   `approved_by = NULL` 만으로는 부족하다. NULL 은 **"사람 승인이 아님"** 과
   **"승인자 기록 버그"** 를 구분하지 못한다. 의도를 담지 못하는 표현으로 감사 사실을
   기록하지 않는다.

   ```
   RuleVersion.origin : 'human_approval' | 'seed'      ← NOT NULL
   ```

   | `origin` | `approved_by` | `ApprovalRecord` | `AuditEvent` |
   |---|---|---|---|
   | `human_approval` | **NOT NULL** | **존재해야 한다** | 승인 기록 |
   | `seed` | `NULL` | 없다 | `actor='system:seed'` |

   - 이 불변식은 **DB 제약·트리거로 강제**하고, 위반이 실제로 막히는지 테스트로 고정한다.
   - `status` 는 `approved` 로 둔다. `status`(판정에 참여하는가)와 `origin`(무엇이
     그것을 승인했는가)은 **다른 축**이다. 시드가 `approved` 여야 2.3 술어에 걸려
     기존 판정이 유지된다.

6. **`effective_from` · `effective_to` 는 양끝 모두 `NULL` 을 받는다.**

   SPEC 2.3 의 술어는 `effective_from <= now < effective_to` 다. 그대로 읽으면 종료일을
   모르는 현행 규칙에 만료일을, 시행일을 모르는 시드에 시행일을 **지어내야 한다.**

   ```sql
   (effective_from IS NULL OR effective_from <= :now)
     AND (effective_to IS NULL OR :now < effective_to)
   ```

   - `effective_from IS NULL` = **시작일 미상**. `effective_to IS NULL` = **무기한**.
   - 시드의 `effective_from` 에 **시드 실행 시각(벽시계)을 넣지 않는다.** 두 가지 이유다.
     첫째, "DB 를 만든 시각"을 "제도가 시행된 시각"인 척하는 것이므로 값 날조다.
     둘째, SPEC 5.3 결정성 테스트는 클럭을 고정하는데, 고정 클럭을 시드 시각보다
     과거로 잡는 순간 전 규칙이 비활성이 되어 판정이 통째로 바뀐다.
     **판정 결과가 DB 를 언제 만들었는지에 의존하는 구조를 만들지 않는다.**
   - `RuleVersion` 불변성(SPEC 2.2)과 `supersedes` 이력 연결을 동시에 성립시키기 위해,
     `effective_to` 의 **`NULL` → 값 1회 전이만** 허용한다. 값→값 재변경, 값→`NULL`
     되돌리기, 그 밖의 모든 컬럼 UPDATE 는 `RAISE(ABORT)` 다. 각각 테스트로 고정한다.

7. **`RuleDraft` JSON Schema (SPEC 4.2.3) 는 아직 만들지 않는다.**

   4.2.3 은 "**판정에 실제로 쓰이는 필드만** 정의한다"고 요구하는데, 그 필드 집합은
   대상 공고문이 특정된 뒤에야 확정된다. 그리고 **수집 대상은 사용자 결정 대기**다
   (SPEC 실사 목록 C). 지금 만든 스키마는 2단계에서 반드시 바뀐다.

   0단계는 규칙 본문을 **불투명 JSON** 으로 저장한다. 대신 2단계에서 스키마만 얹으면
   되도록, 마이그레이션 없이 4.2.1 의 동등성 검증을 붙일 수 있는 형태를 지금 고정한다:

   - `PolicySource` 텍스트는 **저장 시점에 NFC 정규화**(UAX #15). 정규화는 저장 시
     한 번만 한다 — 검증 시점에 다시 주무르면 4.2.1 의 "핵심 방어"가 사라진다
   - `start` / `end` 는 **유니코드 코드포인트 인덱스**. 바이트도 UTF-16 코드유닛도 아니다
   - 구간은 `[start, end)` 반열린
   - `field_path` 는 **RFC 6901 JSON Pointer** 문자열. 지금 파싱하지 않아도 의미는 고정한다

   이 넷이 지켜지면 2단계는 `text[start:end] == 인용문자열` 검사만 얹으면 된다.

8. **주거비 상한 30% 의 준거를 「수도권 임차가구 RIR」로 고정한다.** (사용자 결정 2026-08-13)

   실사(`docs/engineering/diligence/FINDINGS.md` A5)가 모집단 7종을 원문확인했다 —
   전국 임차 15.8 / **수도권 임차 18.4** / 광역시 15.2 / 도지역 12.7 / 청년가구 16.0 /
   신혼 17.7 / 고령 25.4 (2024년도 주거실태조사, 중위수).
   SPEC D-4(서울 중심)에 가장 가까운 **수도권**을 준거로 채택했다.

   **값 `0.30` 은 바뀌지 않는다.** 관측 중위수가 18.4%인데 상한을 30%로 두는 것은
   모순이 아니다 — 상한은 중위수가 아니라 **허용 최대치**다. 다만 그 격차를 숨기지 않고
   `normative_statement` 에 적는다. 30% 라는 수치 자체에는 공표 준거가 없다.

   > **SPEC Part 0-C 의 「RIR 30% 초과 부담 / 50% 초과 과부담」은 준거로 인용하지 않는다.**
   > 2024년도 보도자료 본문에 `30%`·`과부담` 문자열이 0건이고 출처를 확인하지 못했다
   > (FINDINGS.md A5-7). 확인되지 않은 문구를 근거인 척 인용하지 않는다.

9. **DSR 규제 비율을 `safe_debt_ratio` / `caution_debt_ratio` 의 준거로 쓰지 않는다.**

   실사 5절이 정의를 대조해 결론을 냈고 채택했다. **분모가 다르다** — DSR 은 세전 연소득,
   우리 지표는 월 실수령액(세후)이다. 실수령액이 총급여보다 작으므로 같은 상환액이라도
   우리 비율이 항상 크게 나오고, **40%를 그대로 옮기면 우리 지표에서는 오히려 더 느슨한
   기준이 된다.** 분자도 다르다(전 금융권 합산 원리금 vs 프로필 신고 월 상환액).

   두 상수는 `(d) our_choice` 를 유지하고 `source_name` 에 「준거로 삼지 않음」을 명시한다.
   SPEC 2.1 의 「(d)를 (a)(b)(c)인 척하지 않는다」에 부합한다.

10. **`observed_at_unstated` 를 추가한다** (`provenance.schema.json`).

    실사에서 **원문을 확인했는데 그 원문이 기준시점을 밝히지 않은** 행이 7건 나왔다
    (고용보험 요율 연혁표 · HUG 보증료율/보증한도 · 저작권정책 등). 스키마가
    `verified` 에 `observed_at` 을 필수로 걸고 있어 **원문에서 값을 읽고도 승격할 수 없다.**

    | 안 | 판정 |
    |---|---|
    | 조회일을 `observed_at` 으로 대용 | **기각.** 관측 기준시점과 취득 시각의 구분(2.1의 `observed_at` vs `fetched_at`)이 무너진다 |
    | `unverified` 유지 | **기각.** 원문에서 값을 읽었다는 사실이 사라진다 |
    | 「원문 미표기」를 명시적으로 표현 | **채택** |

    통로가 넓으면 "날짜를 못 찾았으니 unstated 로 하자"가 되므로 좁게 연다 —
    `statute/statistic/market` 전용, `verified`/`stale` 전용, `observed_at` 이 `null` 일 때만,
    `source_name`·`source_ref` 필수, `const: true`(끄려면 필드를 뺀다). 음성 6건을 테스트로 고정했다.

    > **Wave 2 숙제.** `dataGrade` 산정(2.4)에서 이 행들은 **`A` 가 아니라 `B` 에 기여**해야 한다.
    > 값은 검증됐지만 신선도를 판정할 수 없기 때문이다. 등급 계산을 구현할 때 반영한다.

11. **생활비의 「주거비 제외」 정의 = 실제주거비 + 공동주택관리비 (47.9%).** (2026-08-13)

    `affordability.living_cost_by_household` 는 **주거비를 제외한** 생활비다. 그런데
    가계동향조사는 가구원수별로 「주거·수도·광열」 **합계**까지만 공표한다. 뺄셈을 우리가
    해야 하고, 무엇을 빼느냐가 판정을 직접 움직인다.

    **판단 기준은 하나뿐이다 — 모델이 이미 주거비로 세고 있는 항목만 뺀다.**
    `engines/tco.py:95-103` 의 주거비 구성요소는 다섯이다:

    ```
    interest · rent · maintenance · opportunityCost · insurance
    ```

    **연료비·상하수도는 여기 없다.**

    | 세부항목 (전체평균, 천원) | 모델이 세는가 | 처리 |
    |---|---|---|
    | 실제주거비 129 | ○ `rent` | **차감** |
    | 기타주거관련서비스(=공동주택관리비) 75 | ○ `maintenance` (`region.maintenanceFeeKRW`) | **차감** |
    | 주택유지·수선 28 | ✕ | 생활비에 남긴다 |
    | 상하수도 26 | ✕ | 생활비에 남긴다 |
    | 연료비 167 | ✕ | 생활비에 남긴다 |

    **차감 비율 = (129 + 75) / 426 = 47.9%**

    ### 기각한 안 — 「주거·수도·광열 전액 차감」

    "공표값만 쓴다 · 우리 가정이 0" 이라는 강점이 있으나 **경계가 어긋난다.**
    전액을 빼면 연료비 167 + 상하수도 26 = 193천원(45.3%)이 **생활비에서도 빠지고
    주거비에도 없는 상태**가 된다. 가구는 실제로 내는데 모델 어디에도 없다.
    1인 기준 353 × 45.3% ≈ **월 160천원만큼 잔여여력이 과대계상**되고 그대로 주거비 상한
    과대로 이어진다. **첫 집 지불능력 도구에서 틀릴 방향으로는 관대한 쪽이다.**

    "우리 가정이 0" 이라는 강점도 이 저장소에서는 성립하지 않는다 — 여기는 우리 선택을
    금지하지 않고 **라벨링을 요구한다**(`our_choice` + `normative_statement`, 결정 #8의
    30% 상한이 그 방식이다). **개념이 어긋난 값을 published 로 표기하는 것보다 개념이 맞는
    값을 `our_choice` 로 명시하는 쪽이 낫다.**

    > 이 기각 근거는 실사 문서가 이미 적어 두었다 —
    > `diligence/excerpts/A2-*.md` 4절 1항 "생활비에서 공과금을 통째로 들어내는 것이라
    > 의도와 어긋날 소지가 크다", 3항 "`maintenanceFeeKRW` 를 주거비에 따로 더하고 있다면
    > 이 조합이 정합적이다". **코디네이터가 요약 표만 보고 4절을 읽지 않아 기각된 안을
    > 권장으로 올렸고, 사용자가 잡았다.** 요약이 아니라 판단이 적힌 절을 읽어야 한다.

    ### 47.9% 는 전가값이다 — `our_choice` 로 표기한다

    전체평균 구성비를 가구원수별에 전가했다. 가구원수별 세부 분해가 공표되지 않기 때문이다.
    ★ 주거·수도·광열은 1인 353 → 4인 572 로 **1.62배**만 느는데 소비지출은 3.0배 늘어난다.
    구성비가 가구원수에 따라 다를 수 있고 **전가 오차의 방향을 모른다.**
    KOSIS 원표에 가구원수별 분해가 있는지 확인 중이며(`W-research-3`), 있으면 전가가
    사라지고 `our_choice` 가 아니라 공표값이 된다.

    ### 감도분석 구간을 함께 고정한다 (SPEC 5.1.3)

    | | 차감 비율 | 1인 생활비 |
    |---|---|---|
    | 하한 (전액 차감) | 100% | 1,454천원 |
    | **채택 (실제주거비+관리비)** | **47.9%** | **1,638천원** |
    | 상한 (실제주거비만) | 30.3% | 1,700천원 |

    감도분석은 이 구간을 교란폭으로 쓴다. 임의의 ±%가 아니라 **정의 선택의 실제 폭**이다.

12. **`observed_at` 규약 — 조사 통계는 조사 실시기간의 종료일.**

    2차 실사가 1차의 표기 오류를 찾았다. 주거실태조사는 **2024년 7~12월**에 실시됐고
    소득은 **2023년 1~12월 월평균**을 물었다. 1차가 적은 `2024-01-01` 은 **조사 실시기간도
    소득 참조기간도 아니다.**

    - **조사 통계** — `observed_at` 은 **조사 실시기간의 종료일**. `T00:00:00+09:00`.
      그 시점 이후의 것은 통계에 들어 있지 않다는 뜻이며, 신선도(2.4)가 묻는 것이 그것이다.
      주거실태조사 2024년도 → `2024-12-31T00:00:00+09:00`
    - **단일 시점 관측**(금리·환율 등) — 그 시점 그대로.
    - **구성요소마다 참조기간이 다르면 `source_name` 에 명시한다.** RIR 은 2024년 하반기
      주거비와 2023년 소득을 섞은 비율이다. 그 사실을 계보에 드러낸다.
    - **공표일은 `observed_at` 이 아니다.** 필요하면 `source_ref` 에 부기한다.
      공표일을 쓰면 조사와 공표 사이의 시차(주거실태조사는 익년 하반기)만큼 신선해 보인다.

13. **모델 상수는 기동 시 1회 읽고 프로세스 수명 동안 유지한다.** (W-platform 질의 2026-08-14)

16. **포맷 골든의 정본 — 정보를 버리지 않는 쪽.** (SPEC 9.1.1)

    파이썬과 JS 가 **이미 다른 문자열을 낸다.** 추론이 아니라 두 구현을 실제로 돌려
    전수 비교했다 — money 20건 중 5건, pct 10건 중 4건이 불일치했다.

    | 입력 | 파이썬 | JS | 정본 |
    |---|---|---|---|
    | `money(25000)` | `"2만원"` | `"3만원"` | **JS** |
    | `money(-750000)` | `"0원"` | `"-75만원"` | **JS** |
    | `pct(25.0, 1)` | `"25%"` | `"25.0%"` | **JS** |

    셋 다 JS 로 갔지만 **JS 를 표준으로 고른 것이 아니다.** 기준은 하나다 —
    **정보를 버리지 않는 쪽.** 세 경우 모두 파이썬이 무언가를 버린다.

    - **`money(25000)`** — 파이썬 `round()` 는 **은행가 반올림**이다. 25,000원은
      2만과 3만의 정확히 중간인데 `round(2.5) == 2` 가 된다. **1만원이 갈린다.**
      이것은 선택된 규칙이 아니라 **아무도 고르지 않은 언어 기본값**이 표시 금액을
      정하고 있던 것이다. 예선의 80만/81만 사고와 같은 부류다. → **half-up.**
    - **`money(-750000)`** — `safe_int` 가 음수를 0으로 클램프 한다. 잔여여력이 음수인
      가구에게 `"0원"` 은 아무것도 알려주지 않는다. `"-75만원"` 은 75만원 모자란다고
      알려준다. → **부호 보존.**
      > `safe_int` 자체는 바꾸지 않는다. 입력 강제에서 음수를 0으로 보는 것은 타당하다.
      > 결함은 **표시 함수가 그것을 쓰는 것**이다.
    - **`pct(25.0, 1)`** — `:g` 는 `"25%"` 와 `"25.0%"` 를 구분 불가능하게 만든다.
      읽는 사람이 정확히 25인지 반올림된 25인지 알 수 없다. F-1 이후 슈바베가
      **측정값**이 되므로 정밀도 표시가 의미를 갖는다. → **고정 소수 자릿수.**

    픽스처는 `contracts/format_golden.json` 이다. SPEC 9.1.1 이 요구한
    **음수 · 0 · 억 경계 · 반올림 캐리 · 소수 자릿수**를 전부 담았고, 그것이 담겼는지를
    `test_format_golden_fixture.py` 가 붙든다.

    > **현행 `common.py` 는 이 픽스처를 통과하지 못한다.** 그것이 이 결정이 고치라고
    > 지시하는 결함이다. 구현 적합성 테스트는 `common.py` 를 고치는 과업이 함께 가져온다.
    > `common.py` 는 지금 W-engines-3 이 1-③ 으로 잡고 있어 직렬화가 필요하다.


    - `attribution` 없이 적재하면 **거부**된다 (음성 테스트로 고정)

    ### 추정 금지를 스키마가 강제한다 (SPEC 4.2)

    - **전 필드 `required`.** 선택 필드를 두면 LLM 이 어려운 필드를 조용히 생략한다.
      원문에 없는 것은 `null` + `not_found` 로 **명시**하게 해서
      「못 찾았다」와 「빠뜨렸다」를 구분한다
    - `not_found` 는 **RFC 6901 JSON Pointer** 배열이며 이 문서 안의 위치만 받는다
    - `additionalProperties: false` — 최상단과 `criteria` 양쪽
    - **파수병 금지.** `ageMax: 200` 은 `maximum: 199` 로 거부된다.
      「상한 없음」은 `null` 이다. 현행 `policies.json` 의 파수병 표현이
      새로 추출되는 규칙에 복제되면 결함이 번진다

    ### span 은 여기 담지 않는다

    `RuleSpanMapping` 이 별도 엔티티이고 `field_path` 로 이 문서의 위치를 가리킨다
    (결정 #7). 그래야 **추출 결과와 근거 매핑이 각각 독립적으로 검증**된다 —
    한 문서에 섞으면 span 검증 실패가 추출 실패와 구분되지 않는다.

> **#19~#30 은 이 문서에 전문이 없다.** 각 PR 본문에 있고 한 줄 색인은
> `docs/engineering/HANDOFF.md` 의 「확정된 결정」 표다. 여기 옮겨 적지 않는 이유는
> 같은 사실을 두 곳에 두면 한쪽만 갱신되기 때문이다 — 이 문서의 「두 종류를 섞지 않는다」와
> 같은 규율이다. **결정의 정본은 PR 본문이고, 이 문서는 계약 파일에 걸린 것만 붙든다.**

31. **`admin` 은 바닐라 JS 로 짓는다 — 빌드 도구를 쓰지 않는다.** (사용자 결정 2026-08-14)

    SPEC 6.2 는 규칙 관리 화면에 한해 빌드 도구를 **허용**한다. 허용은 요구가 아니다.

    | | 바닐라 | Vite + React |
    |---|---|---|
    | 커밋된 산출물 | 없음 | `dist/` — **재생성 diff 강제를 새로 만들어야 한다** |
    | CI | 현행 그대로 (파이썬 전용) | node 툴체인 추가 |
    | 시연 노트북 | 정적 서빙만 | 정적 서빙만 (사전 빌드 동봉) |

    **결정 근거는 새 실패 표면의 개수다.** 커밋된 번들은 D-12 가 `openapi.json` 에 건
    것과 같은 재생성 바이트 비교를 요구하고(1.2 「생성물은 손으로 수정하지 않는다」),
    그 강제 장치 자체가 CI 에 node 를 들여온다. 얻는 것은 상태 관리의 편의뿐이며,
    검토 화면이 요구하는 것(원문 하이라이트 · 필드 diff · 회귀 사례 표)은
    프레임워크 없이 성립한다.

    **되돌리는 조건.** 5단계 구현 중 상태 관리가 손으로 감당되지 않는다고 판단되면
    워커가 `ask` 로 올린다. 그때 이 결정을 다시 본다 — 조용히 빌드 도구를 들이지 않는다.

32. **파생 비율 2종의 산식을 지금 바꾸지 않는다. 편향 크기를 먼저 잰다.** (사용자 결정 2026-08-14)

    > **왜 급한가.** 전세가율이 71.2 → 53.66 으로 떨어지면서 `risk.score` 가 32 → 1 로
    > 급락했다. 실제로 그 값이면 정당한 하락이지만, 지금 그 값은 편향된 산출이라
    > **정당한지 판단할 근거가 없다.** 불변조건 7(틀릴 방향으로는 관대한 쪽을 피한다)에

    둘은 되돌리기 비싸고, 셋 다 **편향의 크기와 방향을 모른 채로는 근거가 없다.**
    측정 결과가 나오기 전까지 두 필드의 계보 표기와 산식은 **그대로 둔다** —
    지금 손대면 무엇이 나아졌는지 잴 기준선이 사라진다.

    측정 산출물은 `docs/engineering/diligence/FINDINGS-6.md` 이며, 재현 스크립트를
    함께 커밋한다. **그 표를 사용자가 보고 산식을 정한다.**

33. **추출 성공률 합격선을 두지 않는다.** (사용자 결정 2026-08-14 · SPEC 4.2.2 · 10.2)

34. **프론트 생성물의 모양 — 파일 4개 · 전역 4개 · 함수 0개.** (D-11, 2026-08-14)

    D-11 이 「`frontend/app.js` 의 판정 사본이 쓰는 상수·정책 규칙은 `ModelConstant` 와
    승인된 `RuleVersion` 에서 생성된다」고 정했다. 그 생성물의 실체를 여기 고정한다.
    **6단계 `web` 워커에게는 이 절이 계약이다.**

    | 파일 | 전역 | 원본 |
    |---|---|---|
    | `frontend/generated/model_constants.js` | `window.FIRSTHOME_MODEL_CONSTANTS` | `store` 의 `ModelConstant` |
    | `frontend/generated/policy_rules.js` | `window.FIRSTHOME_POLICY_RULES` | `store` 의 승인된 `RuleVersion` |
    | `frontend/generated/regions.js` | `window.FIRSTHOME_REGIONS` | `store` 의 `Region` |
    | `frontend/generated/contract_constants.js` | `window.FIRSTHOME_CONTRACT_CONSTANTS` | `contracts/openapi.json` 의 `x-` 확장 |

    - 생성기는 `scripts/gen_contracts.py` **하나**다. `openapi.json` 과 같은 파이프라인이며
      (D-12 가 그렇게 적었다), `--check` · `--stdout NAME` 이 넷 모두에 같은 규약으로 걸린다.
      게이트를 둘로 나누면 한쪽만 도는 경로가 생긴다.
    - 형식은 `머리말 주석` + `window.<전역> = <JSON>;` **한 줄**이다. 빌드툴·CDN 없이

    - 직렬화는 `openapi.json` 과 **같은 규칙**이다 — UTF-8 · BOM 없음 · LF · `indent 2` ·
      `sort_keys` · `ensure_ascii=False`. `.gitattributes` 에 `frontend/generated/** text eol=lf`
      를 걸었다. 걸지 않으면 재생성 비교가 **윈도우에서만** 깨진다 (`contracts/**` 와 같은 사고).

    ### 함수를 내보내지 않는다

    현행 `POLICY_CATALOG` 의 명령형 `rule` 함수는 **생성 대상이 아니다.** 요건 숫자를
    함수 몸통에 박아 두면 그 함수는 백엔드 엔진과 별개로 자라고, 그것이 D-11 이 없애려는
    **두 번째 판정 경로** 그 자체다. 생성물은 `criteria` 필드 집합을 데이터로 내고,
    그것을 해석하는 평가기는 소비자가 쓴다. 그 해석은 `engines/eligibility.py` 와 같아야 한다.

    `criteriaFields` 의 정본은 `rule_draft.schema.json` 이고, 그것이 `eligibility.py` 가
    `crit.get()` 으로 실제 조회하는 키와 일치하는지는 **두 테스트가 각각** 붙든다
    (`test_rule_draft_schema.py` · `test_generated_frontend_diff.py`). 2026-08-14 확인 결과
    **8종이 정확히 일치한다** — `ageMin` · `ageMax` · `annualIncomeMaxKRW` · `assetMaxKRW` ·
    `requireHomeless` · `requireNewlywed` · `requireSME` · `regionPrefixes`.

    ### 키 표기 — 원본의 표기를 그대로 옮긴다

    `store` 에서 온 둘은 snake_case(`source_kind` · `effective_from`), `openapi.json` 에서
    온 것은 camelCase(`clientTimeoutMs`)다. 섞인 것처럼 보이지만 **각각 자기 원본과 같다.**
    생성기에서 표기를 다시 정하면 그 매핑 자체가 두 번째 계약이 되고 어긋나도 아무도 모른다.
    특히 `provenance` 는 `provenance.schema.json` 과 같은 모양이므로 API 응답의 계보와
    **같은 렌더러**로 그릴 수 있다.

    예외는 `x-` 접두 셋뿐이다 — JS 에서 `obj["x-units"]` 는 대괄호 없이 읽히지 않으므로
    `units` · `rounding` · `boundaryConditions` 로 바꿨고, 그 대응을
    `$generated.sourcePointers` 에 RFC 6901 로 적었다. 값이 계약 파일과 같은지는 테스트가 본다.

    ### 지역은 왜 생성물인가 — 시세가 없으면 로컬 판정은 성립하지 않는다

    SPEC 6.2 오프라인 정의 #2 는 「백엔드 없이도 화면이 뜬다 — 단, **판정 숫자는 생성물이
    있을 때만** 나온다」다. 로컬 판정 경로는 시세 없이 아무 숫자도 내지 못한다. 상수와 규칙만
    생성물로 바꾸고 손으로 쓴 시세를 남겨 두면 **그 자리가 정확히 D-11 이 금지한 침묵
    폴백**이 된다 — 절반만 고친 것이고, 화면은 여전히 출처 없는 숫자로 판정한다.

    `regions[].payload` 는 `Region.to_engine_dict()` 그대로다. `api.read_regions()` 가 엔진에
    넘기는 바로 그 객체이며, 골라 담지 않는 이유는 정책 규칙 쪽과 같다.

    **계보는 두 층으로 싣는다.** `payload.source` 는 `provenance.source_name` 이 한 줄로 접힌
    **화면 문구**이고, 접히면서 `verification` · `observed_at` 이 사라진다. 6단계 화면은
    `dataGrade` 사유를 **원인 유형별로** 보여야 하므로(10.2 6단계) 접히기 전의 것이 필요하다.

    ```
    regions[].provenance        레코드 요약. 필드별 계보의 **최악값** (SPEC 2.4)
    regions[].fieldProvenance   사실 단위. 키는 $factFields 의 8개 이름
    ```

    > **지금은 8필드의 계보가 전부 같다** (`market` · `unverified` · `observed_at` 없음).
    > 시드가 8개 전부 예시값이기 때문이고, 없는 구분을 있는 척하지 않는다는 `store` 의
    > 결정이다(`store/seed.py`). 실거래가에 대응물이 없는 3필드(`maintenanceFeeKRW` ·
    > `marketRisk` · `guaranteeAvailable`)도 **값은 있고 계보가 `unverified`** 인 형태로
    > 드러난다 — 값을 비우거나 `null` 로 두지 않는다. 그것이 SPEC 3.1 이 정한 표기이며,
    > 비워 두면 「수집하지 못했다」와 「출처가 없다」가 구분되지 않는다.
    > 수집이 실데이터를 넣기 시작하면 필드별로 갈린다. **소비자는 그때를 대비해 처음부터
    > `fieldProvenance` 를 읽는다** — 지금 값이 같다고 레코드 요약으로 접으면 갈리는 날
    > 화면만 조용히 틀린다.

    ### 소비자 계약 — 침묵 폴백 금지 (D-11)

    ```js
    // 없으면 undefined 다. `|| {}` 를 쓰지 않는다. 그 한 줄이 D-11 을 무효로 만든다.
    if (!window.FIRSTHOME_MODEL_CONSTANTS) { /* 로컬 판정 경로를 끄고 화면에 명시한다 */ }

    // SPEC 2.3 술어를 **자기 시각으로** 적용한다. 생성물은 승인된 규칙 전부를 담는다.
    var now = Date.now();
    var policies = window.FIRSTHOME_POLICY_RULES.ruleVersions.filter(function (v) {
      var rv = v.ruleVersion;
      return (rv.effective_from === null || Date.parse(rv.effective_from) <= now)
          && (rv.effective_to   === null || now < Date.parse(rv.effective_to));
    }).map(function (v) { return v.payload; });   // payload = 백엔드 엔진이 받는 그 객체

    // 지역은 payload 가 엔진 입력이고, 계보는 옆에 있다. source 한 줄로 접지 않는다.
    var regions = window.FIRSTHOME_REGIONS.regions;
    var region  = regions.filter(function (r) { return r.code === code; })[0];
    // region.payload           -> 엔진에 그대로 넘긴다
    // region.fieldProvenance['maintenanceFeeKRW'].verification  -> 'unverified'

    // 타임아웃은 계약에서 유도한다. 프론트가 숫자를 다시 쓰지 않는다 (SPEC 8.3 #3).
    var bc = window.FIRSTHOME_CONTRACT_CONSTANTS.boundaryConditions;
    function timeoutFor(path) {
      return bc.profiles[bc.clientDispatch.byPath[path] || bc.clientDispatch.default].clientTimeoutMs;
    }
    ```

    - **생성 시각으로 미리 걸러 두지 않는 이유.** 그러면 생성물이 「언제 생성됐나」에
      의존하게 되고, 시행일이 미래인 규칙은 그 날이 와도 영영 나오지 않는다.
    - `payload` 를 투영하지 않고 통째로 싣는 이유. `read_active_policies()` 가 엔진에
      넘기는 것이 바로 이 객체다. 필드를 골라 담으면 「무엇을 골랐나」가 두 번째 계약이 되고,
      엔진이 새 필드를 읽기 시작해도 생성물은 조용히 예전 것만 낸다.
    - `$generated.engineVersion` 은 **약한 신선도 토큰**이다. 셋이 같은 실행에서 나왔는지,
      백엔드가 닿을 때는 `/api/meta` 의 `engineVersion` 과 같은지를 확인할 수 있다.
      SPEC 8.4 상 이 값은 판정 출력이 달라질 때만 오르므로 **숫자를 바꾸지 않는 변경은
      잡지 못한다.** 그 한계까지가 이 토큰이 약속하는 전부이며, 재생성 diff 테스트가 정본이다.

39. **신선도를 판정하지 않았을 때 `dataGrade.grade` 는 `null` 이다. `A` 를 낼 수 없다.**
    (W-api-d13 질의 2026-08-15, 승인 · SPEC 2.4)

    **SPEC 2.4 의 `A` 는 두 조건의 곱이다** — 「입력 전부 `verified` **이며** 신선도 기준
    이내」. 신선도 임계가 아직 없으므로 뒤 절이 **확정되지 않는다.** 확정되지 않은 것을
    참으로 읽어 `A` 를 내면 그것이 SPEC 2.4 가 금지하는 낙관적 등급이다.

    | | |
    |---|---|
    | `unverified` 있음 | `C` |
    | `stale` 또는 `pending_review` 있음 | `B` |
    | 그 외 · **신선도 판정됨** | `A` |
    | 그 외 · **신선도 미판정** | **`null`** — 등급을 산정할 수 없다 |

    **기각한 대안:** 「`A` 를 내되 신선도 표기만 옆에 붙인다」. 등급은 **한 글자로 읽히는
    요약**이고 표기는 그 옆에 있다. 요약이 낙관적이면 표기는 변명이 된다.

    ### 조건 — `null` 이 「문제 없음」으로 읽히지 않게 한다

    `grade` 가 `null` 이면 **`reasons` 에 그 이유가 반드시 실린다.** 원인 유형을 하나 더 두어
    (`stale` · `unverified` · `pending_review` 와 나란히) **왜 산정할 수 없는지**를 말한다.
    빈 `reasons` 와 함께 `null` 이 나가면 소비자는 그것을 「깨끗함」으로 읽는다.
    **없는 것을 있는 척 하지 않는 것과, 없다는 것을 말하지 않는 것은 다르다.**

    ### 지금은 도달 불가다 — 구조만 둔다

    시드에서 지역 8필드와 상수 여러 건이 `unverified` 라 등급은 **항상 `C`** 이고 `null`
    분기는 도달하지 않는다. `pending_review`(5단계 산출물)와 같은 처지다.
    **구조만 두고 없는 것을 화면에 그리지 않는다.** 신선도 임계가 등재되는 날 표기와
    `null` 분기가 **자연히 꺼진다.**

    > 임계 자체는 여전히 미정이다. SPEC 2.4 의 「값을 감으로 정해 코드에 박는 것을
    > 금지한다」를 지키는 것이 이 결정의 목적이며, **정하지 않은 것을 정한 척하지 않는다.**
